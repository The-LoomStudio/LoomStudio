# 代码审计：流程与专项入口

本组文档供开发者和 AI 在安排审计、排查 Bug 或理解风险时按需阅读。有时间做系统审查时，先读本页，再选择相关专项；日常局部修改不要求通读，也不因读到检查项就自动产生修复任务。

这里保存判断方法和检查方向，不保存某次审计结论，不冻结领域模型。当前行为看源码与执行证据，应保持的合同看正式 Architecture 与已确认决策；两者冲突时记录偏移。历史问题必须重新核实，不能直接重报。

## 按目标选择阅读范围

| 入口 | 适用范围 |
| --- | --- |
| [前端审计方向](audit-frontend.md) | React 状态、查询与草稿、异步交互、流式阅读、UI/SCSS、渲染安全和前端资源成本 |
| [后端审计方向](audit-backend.md) | RPC、Runtime、持久化、Agent 恢复、Prompt、扩展与 Script、跨端契约和服务端资源成本 |
| [代码审查指南](code-review.md) | 现有分层与 PR 审查规则 |
| [审查工作指南](../workbench/reference/audit-playbook.md) | 历史案例、反证方法、Issue 关闭和延期口径；按相关章节查阅，不复制历史问题 |

前后端分篇只是方便选路，跨端链路仍需追到底。例如保存失败既要检查前端草稿与提示，也要确认后端提交是否已经成功；不能停在一侧的接口签名。

## 先精简还是先修复

先确认行为与责任边界，再按依赖安排修改，不执行“全仓精简完才查 Bug”的流水线。

| 情况 | 处理顺序 |
| --- | --- |
| 已证明没有消费者的旧分支、死参数、孤立样式 | 在已授权实施范围内先删除，再审保留路径 |
| 重复状态、双写或重复调度本身造成错误 | 确认唯一所有者，将修复和收敛作为同一根因处理 |
| 权限、事务、取消、恢复或持久化语义不明确 | 先确认合同与失败场景，再判断哪些路径能合并 |
| 存在可达的数据损坏或高影响安全缺陷 | 优先处理，不等待其他精简完成 |
| 只有相似外观或抽象偏好，没有净维护收益 | 保留现状，不制造施工项 |

检查项是线索，不是缺陷判据。文件长度、重复次数、布尔参数数量、`any`、`catch`、缺少 `useMemo` 都不能单独证明问题。代码是否由 AI 生成也不改变证据标准。

## 一轮审计的最小流程

1. **限定范围与模式。** 选一条完整业务链或少量紧密相关模块，明确只读审查还是已授权实施；未说明实施时只读。全仓目标可按业务链分批覆盖，不能把入口筛选写成逐行全覆盖。
2. **建立基线。** 核对工作区修改、相关局部 README、Architecture 和现有 Issue/Plan。只读影响判断的资料，保留其他任务的改动。
3. **追踪所有权。** 从 UI、RPC、SDK、事件或脚本入口，追到编排、状态所有者、持久化、事件/投影和消费方；补上取消、恢复与销毁路径。
4. **寻找反证。** 查生产消费者、注册表、动态加载、公开 SDK、相关独立扩展、测试与脚本。确认相似对象是否分别承担草稿、快照、缓存、投递或恢复职责。
5. **形成发现并排序。** 区分已确认缺陷、可证明的精简、待核实候选和产品/契约决定。同根因只保留一个处理项；缺陷按影响排序，精简按净维护收益排序。
6. **实施与验证。** 有实施授权时，施工前复核受影响源码，完成职责完整的修改后集中验证；普通实现选择不反复审批，产品和公共合同变化按既定决策边界处理。
7. **记录与收口。** 在现有 Issue 或对应报告中记录结果、未验证范围和延期去向，不另建平行台账。允许本轮没有成立问题。使用 CDP / Console 后，同轮将新增的已验证操作、工具限制和可复用反证同步到[前端 CDP 指南](frontend-cdp-diagnostics.md)，不只留在聊天或 Issue 日志；没有新经验时不重复追加。具体问题状态不搬进指南。

所有权至少回答：谁创建、写入、读取、取消和释放；哪份是权威；操作绑定什么对象、分支、版本和 Run；成功在何处成立，失败时哪些副作用已发生。

## 发现的最小证据

Bug 要写出“触发条件 → 可达调用链 → 错误结果 → 用户影响”。并发问题给出具体交错顺序，性能问题区分已测瓶颈和待测候选。未知行为不能写成确定缺陷。

精简项要说明具体删除什么、责任由谁接管、输入/顺序/错误/取消/持久化语义为何保持，以及新增抽象和调用方复杂度是否抵消收益。零静态引用不等于可删除公开或动态入口；仅透传的包装也可能承担权限、日志、错误转换或公共契约责任。

每条发现使用以下字段；现有报告有同义字段时沿用，不要求重排格式：

```text
编号 / 类别 / 标题：
基线与范围：日期、源码范围、影响结论的工作区改动
位置：可定位路径、符号和当前行号
场景或冗余：调用者、触发条件、实际影响或减少的维护入口
证据与反证：完整因果链、排除的解释、尚存证据缺口
处理方案：最小删改、保留合同、依赖顺序、是否需要产品决定
验证：最小验证目标、实际执行结果、未验证范围
跟踪：与既有 Issue 的关系、当前状态和后续去向
```

删除项给出删除范围即可；确需替代实现时提供最小签名或代码骨架，并标明未经执行验证。不要为了满足输出格式发明新组件、Hook、Repository 或统一管理器。

## 验证与使用边界

- 专项方向按范围标记“已检查 / 不适用 / 未覆盖”，不要求每个方向产出问题。
- 复用现有检查与真实路径，选择能回答主要风险的最小验证；不默认串行运行 lint、typecheck、test、build，也不默认增加测试代码或建立测试体系。
- 同步映射、简单文案和静态样式通常核对 Diff 即可；跨层类型、事务、异步交错、打包边界分别选择相应检查。遵循当前任务约定与[测试准则](testing.md)。
- 静态核查、mock、SSR、本地测试不替代真实 DOM、Provider、进程重启或生产验收。仅有历史通过记录，也不能描述为本轮通过。
- DOM、尺寸、焦点、点击、网络或性能有明确疑点时，按假设做定向诊断；主观视觉验收默认由用户完成。
- 真实数据修改、计费 Provider、远程安装和发布遵守已有授权范围；本文不授予额外执行权限，也不创建定时任务。
- 主要风险已有证据且没有未解释结果后停止。无关旧失败如实记录，不借审计扩展为全仓治理。

可用于发起一轮审计的简短指令：

```text
按 docs/guide/audit-workflow.md 审查【业务链/模块】。
本轮模式为【只读审查/已授权实施】，重点为【检查方向】。
按需读取前端和后端专项，追完整调用链并主动找反证。
输出成立问题、待核实项、覆盖范围和实际验证证据；没有问题可以明确说明。
```
