# 后端审计方向

供 Node.js、Runtime、数据与扩展边界审计按需选读，流程、证据与输出要求见[审计入口](audit-workflow.md)。以下是检查问题，不是当前缺陷清单，也不要求每轮全部执行。

从 [Workspace 任务路由](workspace-development.md)进入 Server、Application Runtime、Application Data 或基础包。遵守[架构规则](architecture-rules.md)：Server 是组装与传输入口，业务归领域 Runtime，底层不反向依赖应用，`shared` 不作为跨域业务实体集合。

## 1. RPC、输入校验与错误传播

**检查什么：**

- 沿 tRPC procedure、现有 parser/Schema、Runtime 和 Store 检查参数、上下文、scope、版本及取消信号是否完整传递。
- 相同输入是否被无必要地二次解码；参数重建是否丢弃有意义的字段、缺失值语义或错误信息。
- 错误是否被吞成空数据或成功结果，是否在多层重复记录；边界转换是否保留可序列化的分类与必要上下文。
- 路由校验能否覆盖所有入口，SDK、工具和内部 Runtime 调用是否绕过它；授权、当前版本与业务约束由谁保证。
- 请求断开是否只停止观察，还是按当前合同取消执行；不要从 HTTP/SSE 连接状态推断业务状态。

**避免误改：** 不照搬 Express Controller 的 `asyncHandler` 或响应包装器，优先核对现有 tRPC 边界。不机械替换专用 parser，不把 Zod 扩散到可信内部函数；也不能把事务内 CAS、权限和资源关系检查搬到路由后就删除。

**最小证据：** 一个真实入口的输入、解析结果、Runtime 参数、最终响应和错误链。新增包装前说明当前边界缺少什么职责。

## 2. 领域所有权、跨端类型与事件

**检查什么：**

- 相似类型是否确为同一契约，还是分别表达存储记录、传输 DTO、执行状态和显示投影；同一契约是否已有类型派生或共享 parser。
- 状态枚举、默认值、错误分类、规则和能力目录是否由两个地方独立维护；先找正式所有者与实际消费者。
- 包装和映射是否只是无意义往返，还是承担版本转换、序列化、权限或稳定公共接口。
- Fact、Notification、Stream 和 Lifecycle 事件是否按各自语义发布；提交事实是否在提交后才可见，scope/operation 是否完整。
- 是否用通用数据变更事件驱动特定业务完成，或者维护一套与实际注册/路由漂移的静态目录。

**避免误改：** 不要求全部类型移入 `shared` 或统一 `z.infer`，不把持久化实体原样作为公共 DTO；读取/写入合同不同也不能强行共用 Schema。`Pick/Omit/Partial` 只有在语义一致时才是复用。

**最小证据：** 列清所有者、写入者、消费者及边界转换。核对实际字段和发布时机，不能只以 TypeScript 可赋值证明行为一致。

## 3. 事务、CAS、删除与文件一致性

**检查什么：**

- “先检查再写入”是否允许可达交错；保护是否由同事务、唯一约束、版本 CAS 或其他现有机制提供。
- 关系/所有权检查与写入是否隔开；多个 Store 的操作是否真的共享事务，而不是名字相同的独立提交。
- 数据库、文件和 Blob 的提交/清理顺序，部分失败后是否遗留孤儿，是否误删共享字节或已被其他操作采用的资源。
- Timeline、Session、Workspace、扩展作用域和归档引用的删除与恢复是否遵守当前生命周期。
- readback 是否承担规范化或版本返回；导入导出是否保持字节、MIME、特殊 JSON 键和引用关系。
- 缺失软引用是否按合同允许，不能自行升级为禁止删除、自动改绑或全局引用管理机制。

**避免误改：** 不为每段操作增加事务、重试或补偿管理器。先确认实际原子边界和正确恢复方式；取消不等于回滚，跨文件与数据库的业务流程也不能仅靠一个 JS `try-catch` 宣称原子性。

**最小证据：** 给出交错或故障注入点以及提交前后的事实。使用隔离临时数据和真实 Store/文件路径验证主要风险；纯 mock 不能证明 SQLite、文件系统或崩溃恢复。参考[数据架构](../architecture/data/README.md)。

## 4. Agent、Narrative、Prompt 与执行恢复

**检查什么：**

- 按[当前 Runtime/Session 合同](../architecture/application/agent/runtime-and-session.md)确认 canonical 内容、正文索引、工具事实、分支、轮次和候选的归属。
- 用户输入保存、Run 启动、Provider Step、工具结果、正文采用与最终完成之间，是否存在丢记录、重复采用或错误的成功时机。
- 暂停、取消、失败、观察断连和执行器停止是否正确区分；检查点是否处于可恢复的安全位置。
- 重试/恢复是否重复执行已完成工具，是否在副作用不明确时猜测成功；请求身份相同但参数不同的情况如何处理。
- 旧任务的晚到结果是否还能写入已切换的 Branch 或过期版本；恢复是否遵守当前预设、工具合同与权限。
- 剧情摘要、工作摘要、Workspace 记忆的来源范围、采用版本、退休边界和失败行为是否相容。
- [PromptBuild](../architecture/application/prompt-build/README.md)的来源、锚点、排序、激活、文本规则、历史投影和 Token 口径是否准确；预览与执行是否遵守各自声明的输入，转换有无遗漏或重复。

**避免误改：** 不把摘要生成与摘要采用视为同一步，不把投递记录、流式缓冲、持久事实和恢复检查点按字段相似合并。不从历史计划硬编码旧 Session/Timeline 关系，不自动补造工具结果或恢复旧兼容路径。

**最小证据：** 选定一条输入到持久化/恢复的完整链，明确每个中断点的事实与下一步。Fake Provider、受控工具和临时数据库可验证部分合同；真实 Provider 与重启恢复只有实际执行后才能声称通过。

## 5. Extension、Script 与宿主生命周期

**检查什么：**

- Manifest 声明、授权、激活、实例状态是否分别准确；注册配置和运行结果是否被误作重复状态。
- 安装、启用、挂载、刷新、热重载、卸载和销毁是否有唯一编排者；旧实例的订阅和晚到回调是否被释放或拒收。
- 实例绑定的角色、Timeline、installation 和 capability 是否在执行时仍有效；客户端声明是否被错误地当作宿主授权。
- SDK、RPC、注册表、动态入口和独立扩展实际消费的公共能力是否一致；无主仓静态引用的导出是否仍属于发布合同。
- Script 各执行器、Worker、iframe 与宿主桥接的能力和清理职责是否清楚，是否把运行隔离冒称安全沙箱。

**避免误改：** 不因两层都处理生命周期就删除其中一层；先区分宿主实例、执行器和消费者的责任。不要为消除静态扫描告警删除必要的扩展发布形式，也不要为统一执行器扩大权限。

**最小证据：** 从真实创建入口追到退出，观察实例身份、订阅与消息归属。参考[扩展架构](../architecture/extensions/README.md)和 [Script Runtime](../architecture/extensions/loom-script-runtime.md)；模拟 Worker 不证明真实 Worker 终止或加载成功。

## 6. 路径、网络、秘密与外部内容

**检查什么：**

- VFS、真实文件路径、压缩包条目与符号链接如何保持授权范围；路径拼接本身是否被误当作边界校验。
- Provider、下载、代理和扩展网络请求的目标由谁控制，是否可以跨越实际信任边界；重定向等处理是否仍符合策略。
- 本地部署、远程访问、HTTP/WS 与扩展调用各自采用什么身份和来源检查；对象归属或 capability 是否在实际执行点验证。
- 输入是否能通过宽泛对象赋值修改未授权字段；输出 DTO、日志、Trace 与错误是否泄露凭据或不该返回的数据。
- 外部 JSON、压缩包和脚本是否存在实际可达的大小、深度或执行资源风险，现有边界是否已处理。

**避免误改：** 不把单用户本地应用套成多租户 SaaS，也不因本地部署就忽略外部入口。项目可能需要本地 Provider，不能一律屏蔽内网地址；先确认具体攻击者可控输入和授权能力。复用现有 Secret Store、路径/parser 与 Host 边界，不叠加猜测式 fallback。

**最小证据：** 明确攻击者可控什么、经过哪些检查、最终获得什么未授权能力。只有危险 API 名称、依赖告警或理论输入时，先列候选，不直接宣称可利用漏洞。

## 7. 查询、事件循环与资源成本

**检查什么：**

- 相同读取、权限解析或字段投影是否在一条链重复执行；列表是否逐项查询形成 N+1，单项消费者是否拉取全量历史。
- 分页、排序、过滤和导出是否各自保持完整消费合同；缩小查询是否会改变上下文相关计算。
- 独立异步操作是否无必要串行；并行前确认顺序依赖、事务连接、限流、共享状态与失败语义。
- 大文件、JSON、压缩、哈希或文本处理是否阻塞事件循环或全量缓冲；缓存、队列、日志和流式慢消费者是否有实际增长路径。
- 重试是否重复成本或副作用；缓存失效、容量和实例释放由谁维护。

**避免误改：** 不机械把 `await` 改成 `Promise.all`，不为所有读取加缓存、Repository 或 Stream 包装。重复查询先考虑已有 Store 的批量能力和消费者范围；精简必须减少实际工作，而非仅把重复搬进 helper。

**最小证据：** 固定消费者和数据规模，记录查询次数、耗时、事件循环或内存指标；区分可达复杂度问题、微基准与端到端收益。没有测量的收益明确标为预期，不据此承诺生产表现。

## 跨端交接时带走什么

与[前端专项](audit-frontend.md)共同核对实际输入、对象/版本身份、提交点、错误码、事件范围和重试语义。后端返回成功不证明界面采用正确，前端提示失败也不证明写入回滚；两侧应指向同一条事实链和同一个根因记录。
