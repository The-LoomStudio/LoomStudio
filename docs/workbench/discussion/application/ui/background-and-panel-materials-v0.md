# 背景、面板材质与扩展 UI

> **状态**：Open Design / Discussion Capture
> **日期**：2026-09-10
> **推进关系**：与背景系统同步设计、实施和验收；本次只记录讨论，不授权代码修改。

## 1. 目标与边界

透明面板、半透明底色和毛玻璃属于 Studio 第一方外观能力，不依赖扩展提供。背景可以来自官方图片背景或扩展 Renderer，包括动态 Canvas / 3D 场景。

当前重点不是插件如何修改宿主样式，而是宿主如何管理 CSS Token、DOM 层级、动画与背景采样，避免毛玻璃在真实布局中失效，只剩透明底色。

现有合同仍以 [CSS 与主题](../../../../architecture/ui/css-and-theming.md) 和 [Client Renderer Host](../../../../architecture/extensions/client-renderer-host.md) 为准。外部样本见 [Engram / The World 参考](../../../reference/st-extension-rendering-engram-the-world-reference.md)。

## 2. 已确认方向

- 材质与背景系统共同推进，不把毛玻璃作为孤立的组件样式补丁。
- Token 负责参数，容器结构负责采样边界；仅统一颜色和 blur Token 不足以保证效果。
- 背景渲染与宿主材质分工：Renderer 画背景内容，宿主控制面板底色、模糊与可读性。
- 不把所有已有 `surface` Token 直接改成透明色，不默认给每个深层组件添加毛玻璃。
- 真实浏览器视觉与性能验收是必要条件；属性存在、类型检查或 CSS 编译通过不能替代验收。

## 3. 采样边界

Backdrop Root 与 stacking context 不是同一个概念。不能把毛玻璃失效统一归因为 `z-index`，也不能认定所有 `transform` 都截断背景采样。

根据 [Filter Effects Level 2 草案](https://drafts.csswg.org/filter-effects-2/)，祖先上的 `opacity < 1`、`filter`、`backdrop-filter`、mask、`clip-path`、混合模式及相关 `will-change` 可能形成背景采样边界。需要结合具体属性值与目标浏览器验证，不把这份草案当成跨浏览器效果保证。

排查时至少区分：

- 祖先改变采样边界，目标背景位于边界之外；
- 中间不透明底色遮住目标背景；
- 材质本身底色过实，或背景缺少足以观察模糊的纹理；
- 裁切、尺寸、动画或浏览器实现导致结果不同。

整体 `opacity` 不作为背景透明度控制：它还影响文字、按钮与整个元素的合成结果。背景透明度应通过底色 alpha 表达。

## 4. 候选结构

```text
Stage
├─ Background
└─ PanelShell
   ├─ MaterialPlane
   └─ Content
```

- `PanelShell` 负责布局、位置与尺寸。
- `MaterialPlane` 负责底色、背景模糊与边框。
- `Content` 负责内容、滚动及内部交互。

这是职责划分，不要求新增同名组件或固定使用额外 DOM。具体采用伪元素还是独立元素，实施前根据现有组件核定。

候选约束：

1. 中间布局 wrapper 默认不附加滤镜、整体透明度或材质效果。
2. 一块面板优先只有一个材质背板；输入框、列表项等内部表面使用普通色块。
3. 滚动内容与固定材质背板分离，避免背景效果跟随内容无意滚动。
4. 不默认对包住玻璃的祖先做整体 opacity 入场动画；内容、底色和几何动画分别设计并验证。
5. 弹窗、浮层和 Portal 使用约定挂载层，不通过任意父级加极大 z-index 修补。

背板不能绕过祖先的 Backdrop Root。结构分层是为了减少意外，不是隔离所有 CSS 问题的万能方案。

## 5. 候选材质 Token

保留现有颜色体系，仅为真正的材质区域增加必要参数。以下名字是示意，尚未冻结：

```css
--loom-material-panel-fill
--loom-material-panel-blur
--loom-material-panel-border
--loom-material-panel-solid-fill
```

实色、半透明、毛玻璃和透明模式映射为同一组材质参数，不让各业务组件独立拼装颜色与滤镜。底色不透明度和模糊强度分开控制。

需要在实施时明确参数覆盖哪些区域，避免 CSS 变量继承导致输入框、嵌套面板和弹窗意外采用同一玻璃配置。是否保留不透明模式、如何处理不支持滤镜及用户可读性偏好，需要与背景设置一起收口。

## 6. 与背景系统共同验收

采用一个最小材质样例，覆盖带纹理的静态背景及动态背景，检查：

- 静止面板、开关动画和动画结束后的效果是否一致；
- 内容滚动、嵌套内容、弹窗与 Portal 是否保持预期采样；
- 桌面与移动端目标浏览器的实际表现；
- 多面板叠加时的性能、文字对比度与交互可读性；
- 切换背景或材质模式后，是否残留旧样式与图层。

优先在少量宿主区域应用毛玻璃，不默认给每条消息单独增加滤镜。实际性能上限应测量后确定，不承诺固定帧率或任意数量叠加。

`@supports` 只检测属性支持，不能确认采样到了正确的背景。诊断先检查目标与祖先的计算样式、底色、几何和采样边界，再判断是否为浏览器问题。

## 7. 开放问题与非目标

实施前需要收口：材质覆盖区域、默认模式、现有动画需要调整的位置、Portal 挂载层、降级表现及目标浏览器。

本讨论不建设任意 CSS 注入系统、多背景插件编排器、新主题引擎或完整 Renderer 沙箱；不改动正在执行的文本管线计划。

## 8. 扩展声明式设置页

本节补充同属渲染与 UI 的作者体验课题，不表示设置页必须与背景材质在同一批次实施。

### 当前事实

2026-09-10 核对 [Client SDK](../../../../../packages/extension-sdk/src/index.ts) 与 [Renderer 工作台](../../../../../apps/studio-client/src/features/extension-renderers/ui/renderer-workspace-panel.tsx)：

- 已有工作台 Action / Command 和 `shell.workspace-panel` 自定义界面挂载。
- 官方扩展管理页使用 Master–Detail，但内部组件不等于对作者开放的页面模板 API。
- 本次未找到可供作者声明字段、由宿主自动生成设置页的公开合同，也未找到通用列表 / 详情模板 API。
- Client Context 没有直接配置读写入口；不能把现有后台配置存储当成已完成的作者表单闭环。

### 建议方向

优先提供声明式设置页，不先建设通用 UI DSL 或页面模板引擎：

- 作者声明字段、默认值、选项与约束，必要的业务校验通过受控入口执行。
- 宿主负责开关、输入框、选项控件、布局、错误反馈、保存状态、无障碍与移动端适配。
- 简单配置由官方 UI 渲染；地图、游戏面板等复杂界面仍由作者通过 Renderer 实现。
- Registry 记录实现和挂载声明，Host 调度挂载 / 更新 / 卸载；自定义 Renderer 的内部绘制仍由作者负责。

示意内容：

```text
天气设置
├─ 启用天气效果：开关
├─ 特效质量：低 / 中 / 高
└─ 音量：数值
```

扩展工作台左侧目录选择“设置”，右侧就地显示官方表单，不跳转到独立的表单管理中心。自定义 Renderer 与官方设置页可以属于同一个扩展。

### 数据与实施边界

优先复用既有 Extension Config 能力，不建立表单专用存储。实施前必须确认配置 Scope、声明来源、默认值语义、读取 / 保存权限、并发更新与校验失败行为；本讨论不冻结具体 Schema 或新增 RPC。

通用列表、Master–Detail 模板和组件 SDK 保留为后续需求，不能因设置表单有价值就一并扩大范围。进入实施前单独制定最小计划，并验证真实作者声明到保存读取的闭环，而非只有静态表单截图。
