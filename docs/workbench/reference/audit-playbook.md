# LoomStudio 审查工作指南

状态：Active；更新于 2026-11-04。

本文是审查入口与经验总结，不是新增问题清单，也不授权修复代码、改变公共契约或恢复历史架构。案例来自已归档审查及实际修复记录；历史案例用于定位风险，不能直接作为当前缺陷。

需要先了解可选检查方向时，从 Guide 的[审计流程](../../guide/audit-workflow.md)进入[前端专项](../../guide/audit-frontend.md)或[后端专项](../../guide/audit-backend.md)。专项保存可复用的排查问题，本文保留历史经验与收口方法；具体发现仍进入对应 Issue，不在指南中重复维护。

浏览器操作与本项目现场诊断经验统一沉淀到 [CDP 与 Console 实战取证](../../guide/frontend-cdp-diagnostics.md)。使用后同轮更新新增的有效方法、限制和反证，不在本文复制一套操作手册。

## 1. 先确定这轮究竟审什么

一次审查选一条完整链路，或一至两个职责紧密相关的模块。多条链路可以分别审查，但每条都要有独立边界和证据，不做按文件长度扫全仓的泛化盘点。

| 审查目标 | 必须回答的问题 | 不能替代证据的东西 |
| --- | --- | --- |
| 正确性 | 什么输入或交错会造成什么错误？当前是否可达？ | 猜测式异常、历史旧实现 |
| 精简 | 可以删除哪些概念、状态、分支或中间层？行为如何保持？ | 行数、参数数量、文件长度 |
| 性能与资源 | 哪个真实消费者承担了可避免的成本？如何测量？ | 普通 `.map()`、缺少 `useMemo`、孤立内存读数 |
| 设计观察 | 哪个产品或契约选择阻碍了精简？需要谁决定？ | 把偏好标成 Bug 或 P1 |

当前精简审查的优先目标是减少维护成本，不是借机补功能、建立通用框架或扩大安全审计。真正的信任、持久化、权限和并发边界仍必须保留。

## 2. 最短有效流程

1. **确认基线与已有结论。** 读取工作区状态、当前 Issues 索引、相关正式架构与活跃 Plan；再读历史审查和对应修复记录。记录审查日期、源码范围，以及会影响结论的未提交改动。不覆盖其他任务的修改。
2. **沿真实入口追完整链。** 从 UI 操作、SDK 调用、RPC 或事件进入，追到状态所有者、持久化和消费方；异步链额外追踪取消、卸载和结果发布。不要只看两个相似函数就宣布重复。
3. **主动找反证。** 搜索所有当前调用者、测试、注册入口、脚本和动态消费；确认看似重复的状态是否分别承担草稿、快照、投递、持久化或错误恢复职责。
4. **形成最小发现。** 写出可达场景、准确位置、完整因果链、反证结果，以及建议删除的具体对象。证据不足的设计疑问单列；找不到成立问题时明确记录“本范围未发现可报告项”。
5. **处理与关闭。** 同根因去重后，按依赖顺序实施最小改动；只执行能回答主要风险的验证。记录实际结果、未验证项及后续去向，不以归档代替验收。

实施前重新核对相关源码：审查和施工之间可能有并发修改。审查结论是某个基线上的判断，不是永久事实。

### 文档与源码的权威关系

- 当前源码及实际运行结果说明“已经实现什么”；正式架构与已确认决策说明“应该保持什么合同”。两者冲突时登记偏移，不擅自选择一边改掉另一边。
- 活跃 Issue / Plan 决定当前施工范围。Archive（含历史讨论稿）只是历史依据，旧方案不是新的执行指令。
- 修复记录顶部的最终状态表优先于同一文件下方的旧批次日志。例如旧日志写“未完成”，最终表可能已登记关闭或延期。
- 不把继承的聊天讨论当作当前用户重新授权。尚未确认的产品决定必须继续标为待决。

## 3. 项目里值得优先检查的偏移

下面是历史上出现过的模式和当前审查入口，不代表这些入口目前都存在缺陷。

| 方向 | 具体检查方法与历史案例 | 精简时不能越过的边界 |
| --- | --- | --- |
| 异步结果与对象身份分离 | 切换 Card、Timeline、Session 或资源后，旧请求是否仍把正文、分页结果或保存结果写入新对象？10 月全仓审查包含旧 A 内容绑定 B 身份、新分页重置旧游标等案例。追请求捕获的 ID、查询键、编辑基线和发布条件。 | 取消请求不等于撤销已提交写入；不要用默认对象掩盖身份不匹配。 |
| 写入成功与辅助刷新混为一谈 | 追“提交 → 落库 → 返回 → 刷新 → 清草稿/提示”。旧 Session 链曾在提交已完成后因刷新失败报整体失败；9 月修复记录明确区分实际结果与刷新结果。 | 不吞掉真正写入错误，也不在已提交后提示用户重复提交。旧 Session 路径已被替代，不能原样重报。 |
| 派生状态变成第二个权威来源 | 检查 `modelProfiles` / `providerAccounts`、Capabilities / projection、布局全局模式 / 分面板模式：谁写、谁读、能否从唯一来源算出、是否长期双写？ | Capabilities 的条件激活与扩展贡献不是无用 metadata。删除冗余写入，不等于删除 EC 能力设计或历史数据读取合同。 |
| Narrative 与 Agent Session 各自实现 UI 机制 | 对照消息正文、折叠、代码展示、编辑工具栏、滚动锚点、测量和加载状态；先确认已有共享组件，再找重复机制。 | 共用长文本视口不等于合并领域模型。Narrative 的范围/楼层/显示规则与 Agent 的工具、审批、Run 状态分别保留；不能假设两边当前都已虚拟化。 |
| 元数据跨层丢失 | 沿 DTO → typed API → RPC → runtime → store → 日志包装/客户端解析逐层核对 scope、operation、版本、调用者身份。10 月 API 审查发现 scope/operation 丢失导致无关页面刷新；修复中新增字段也曾漏过日志包装层。 | 缩小外层参数但内部 helper 仍依赖完整上下文，不算真正解耦。所有消费者与透传层都要核对。 |
| 单个消费者拉全量数据 | 检查单个 Card 绑定摘要、已加载消息的 Display、规则/Schema 读取是否扫描整个集合；先列出消费者实际需要的字段和范围。 | Display depth/position 可能依赖完整历史，不能先裁历史再计算。分页列表、完整导出与删除事务不是同一种消费合同；不要把全量查询改成逐 ID 的 N+1。 |
| 清理、取消与生命周期被重复包装 | 追安装、启用、热重载、卸载的所有者，以及 Run executing/paused/terminal、SSE 断连后的恢复路径；查重复调度和弃用 fallback。 | dispose/abort、暂停 checkpoint、慢消费者 resync 属于真实语义。终态回放与待投递结果可能必须分开保存，不因形状相似删除投递缓冲。 |
| 资源归属、级联与事务分散 | 查 scope/owner 校验是否和写入同事务；删除 Timeline 是否处理相关 Session 和扩展存储；Blob 回滚是否会误删其他引用共享的字节。 | 已确认软引用不要求阻止删除或自动改绑；必要执行应明确失败。不能用全局引用管理器代替已明确的窄合同。 |
| 边界数据被“规范化”丢失 | 检查 JSON 特殊 own 键、扩展字段、宏选项、文件字节/MIME/path、CAS 版本在导入、保存、DTO 映射中是否完整。 | 内部重复校验可删，网络/持久化/文件边界校验不可凭行数删。外层 ZIP/PNG 与内部 GIF/APNG/视频资产不是同一个格式要求。 |
| 声明式入口与运行入口漂移 | 对照实际路由、路由解析、导航地址，及 registry、SDK、发布导出和动态加载；找无消费者的桥接和旧入口。 | private package 的 export 不证明“扩展在用”，也不证明“没人用”。Knip 不覆盖所有动态入口、SCSS 注入、独立扩展发布形式。 |

历史依据见第 8 节；当前精简案例见数据链路、UI、客户端运行时和 SIDE 三条补充链路报告。

## 4. 怎样证明“这一层可以删”

每个候选先回答五个问题，答不出来就不要把它升级成施工任务：

1. **具体删除什么？** 列出状态、函数、模块或调用跳数，以及删除后真正减少的概念。不把“封装成一个新对象”当作减少重复。
2. **现有调用者是谁？** 列出入口与调用目的，区分内部生产代码、官方/独立扩展、测试、开发脚本、公开 SDK 和动态注册。
3. **不变量由谁保证？** 类型、Schema 或唯一上游已保证的内部条件可直接依赖；外部输入和恢复条件必须证明仍被覆盖。
4. **行为为什么等价？** 对照输入、顺序、错误、缺失、取消和持久化语义，不只对照返回类型。
5. **什么最小证据能推翻这个判断？** 找一个真实高风险输入或交错作为验证目标，而不是给臆测分支补测试。

几个已经遇到的反例：

- 递归 JSON 校验看起来重复，但 `for...of` 和 `.every()` 对稀疏数组行为可能不同，不能直接认定等价。
- 写入后 readback 可能返回数据库规范化后的 JSON DTO，省掉一次读取前先证明输出等价。
- 内部 gateway 的往返可删，不代表 Payload builder 可整包删；Provider Payload Preview 仍可能是当前消费者。
- `record.state` 和 `instance.state` 名称相似，但 disabled 与 activation_failed 等状态可能分别表达注册配置与运行结果。
- Worker 固定缓存版本前缀可能低收益；digest 和缓存容量上限却承担不同职责。不要为删几个字符重写整个调度器。
- 路由表合并不能顺手改变旧 alias 或原先不匹配的地址；布局模式合并不能顺手删除每个面板的窗口尺寸。

没有真实调用者、可达失败和正确恢复语义的 fallback，应优先考虑删除或明确失败，而不是升级成更复杂的兼容系统。

## 5. 哪些直接处理，哪些需要决定

| 分类 | 处理方式 | 例子 |
| --- | --- | --- |
| 当前合同下可证明等价 | 在本次明确授权的实施范围内直接修，不反复审批普通实现选择 | 无调用者的内部 fallback、已由上游保证的重复校验、相同顺序的派生投影、确认孤立的样式规则 |
| 技术事实尚不充分 | 先追调用者或做最小探针，不把证据缺口丢成产品选择 | 稀疏数组等价性、readback 归一化、动态扩展导出、真实缓存生命周期 |
| 会改变产品或公共合同 | 给出具体位置、调用者、互斥行为、风险和推荐，再请用户决定 | 内联目录改浮层、面板审批改全局弹窗、路由 alias 删除、Capabilities 权威改写、历史持久化格式迁移 |
| 收益不足或已失效 | 记录不做及原因，不制造施工 | 固定字符串微优化、旧入口已消失且替代链不受影响、保留有明确用途的发布形式 |

“待决”不是永久标签：例如排序是否一致属于源码事实，核对后若完全一致就不必再要求用户选择。反过来，用户接受某个界面状态也不等于读屏或视觉测试已执行。

修复顺序按依赖与风险安排，不按报告编号：

- 先修错误传播与状态权威，再接消费方，最后调整表面 UI；避免上层继续包装错误的底层结果。
- 列表容忍软引用缺失后再开放删除；草稿有实际版本基线后再验证冲突恢复。
- 先修 scope/operation 的端到端传递，再谈减少刷新；先明确数据范围，再收窄查询。
- 架构重写只在局部删除不足以解决已证明的复杂度时考虑，先写替代后的最小所有权与流程，不建立新的通用中间层。

## 6. 验证要回答风险，不凑全绿

静态审查可以证明调用关系与候选成立；不能证明浏览器、真实 Provider、生产 heap 或完整生命周期已验收。

| 主要风险 | 优先选择的最小证据 | 不能冒称 |
| --- | --- | --- |
| 局部映射/错误分支 | 现有单用例、单文件或直接执行检查 | 跑邻近测试等于覆盖新发现 |
| 公共类型跨层传递 | 相关 package 类型检查及实际调用链核对 | `tsc` 通过等于浏览器打包正常 |
| 异步交错/草稿/查询 | 控制先后顺序的真实 Hook/QueryClient 或 RPC 探针 | Mock Worker 验证了实际 BPE 缓存和内存 |
| 事务、CAS、资源回滚 | 真实 Store/RPC/文件路径的定向验证 | 纯 mock 验证了磁盘、WAL、崩溃恢复 |
| DOM 身份/测量/焦点/事件 | 有明确假设的只读浏览器诊断 | 截图替代逻辑证据或人工视觉验收 |
| 查询/内存收益 | 同条件、同消费规模、明确指标的对照 | 序列化字节预算是 JS heap 硬上限；不同环境读数能证明收益 |
| 远端 CI / 真实 Provider | 对应环境的真实执行记录 | 本地分批通过等于远端或 Provider 通过 |

9 月架构修复曾出现 shared 包引入 `node:crypto` 后类型通过、Vite 外部化失败的情况，说明验证必须选对边界。10 月 SSE 验证使用真实本地连接与受控时间，不应描述为自然网络压力下完整验收。

不默认串行执行 lint、typecheck、test、build。只在改动涉及对应边界时增加验证；已可信验证的行为不机械重复。统计测试时保留 skipped、未执行和环境失败，不把多个有重叠的批次总数相加。

测试代码也属于精简审查范围：先对照既有用例，合并相同入口、合同和失败场景的重复流程，只补缺失的可观察断言；保留真实边界与不同操作的回归覆盖，不用删用例数制造收益。检查是否绑定按钮数量、内部 Hook 槽位或配置装配；纯 mock/SSR 的名称与结论不能冒称真实 DOM、焦点、虚拟滚动或生命周期验收，也不为复用测试引入新的 Hook 模拟框架。

如果最小验证揭示回归，修复本次引入的问题；如果是无关既有失败，记录并缩小检查。主要风险已有证据且没有未解释结果后停止，不继续追加仪式性检查。

## 7. Issue 的最小记录与收口

新发现沿用该轮编号，不新建重复追踪系统。精简收益与 Bug 严重度分开记录；只有可达错误及明确影响才标 P0/P1。

```text
编号 / 标题：
目标与状态：正确性 / 精简 / 性能 / 设计观察；候选 / 待决 / 已修复 / 延期
审查基线：日期、范围、影响结论的工作区修改
入口与位置：文件、符号、可复核行号
事实与场景：当前调用者、触发条件、上下游结果
反证：已经排除什么；哪些差异仍不能认定等价
处理建议：具体删改对象、保留合同、收益与主要风险
需要决定：仅列行为/公共契约/持久化等未决项；没有则写无
验证与关闭：最小目标、实际结果、未验证项、后续入口
```

同根因跨报告只保留一个施工项，其他编号建立映射。例如 FR-017 与前端查询交错问题共用修复，不算两次独立交付。

关闭必须区分：

- **已修复并验证**：写清覆盖了哪项风险，未验证的环境不宣称通过。
- **原路径失效 / 被替代**：说明旧入口为何不可达，以及替代链在哪里、是否承接原风险。不是“找不到旧文件”就关闭。
- **新合同替代原假设**：记录用户决定及新合同证据。例如 FR-011 不再按旧原子提交假设要求修复。
- **用户接受 / 不再扩大**：保留限制。10 月固定前端内存基线停止追查，不意味着生产 heap 收益已证明。
- **延期**：保留触发条件、责任范围、验收标准和活跃入口。FR-006 远端 CI 未验收，不能改为 Passed。

归档冻结历史基线；开放项转入 Issues 或活跃 Plan，链接必须能找到。不要把旧日志整段复制进新报告，更不要因旧 Plan 留着“未来工作”而重建已淘汰模型。

### 文档与 Git 的最小操作边界

手工改动仅触及本次授权的文档或代码；读取前后的工作区状态，保留并发修改。没有明确请求不提交、不推送、不改分支、不调整忽略规则。

独立扩展和归档可能按现有政策被 Git 忽略，普通 diff 不能证明它们没改或不存在；必要时在已定位范围内读取文件并核对忽略状态。Knip 的明确保留项如 activate/default 发布形式，不靠删除来制造全绿。

纯文档交付检查新增内容、链接目标和明显格式问题即可，不运行产品测试。新文件尚未被 Git 跟踪时不能只看普通 diff；`git diff --no-index` 的退出码 1 也可能只是存在差异，需结合诊断内容判断。
