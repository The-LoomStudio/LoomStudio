## 共同流程与各自边界（建议）

共同体验为：检查来源 → 发现候选 → 查看版本与变更 → 准备并预览 → 用户确认采用 → 执行 → 查看结果与后续动作。

- 共同展示对象名称、来源、当前采用版本、候选版本、检查时间、变更说明、本地修改 / 冲突、执行结果。Git commit 与包声明版本分别保留，不靠名称或字符串大小判定身份和新旧。
- 区分作者发布说明、实际内容差异、用户最终选择及执行收据；发布说明不能代替真实 Diff，下载成功不能当作采用成功。
- 版本检查与提醒不下载并执行代码、不替换内容、不扩大授权。准备下载与执行采用是明确的后续动作。
- 检查失败应与“已是最新”区分；按来源 / 候选版本去重提醒，支持稍后处理。后台检查频率、忽略版本是否持久化及跨重启提醒策略待确认。
- 沿用现有通知入口；先满足应用内待处理状态与结果查询，不为此建设通用通知中心、Web Push 或后台常驻服务。日志里的提交事件通知不是用户更新提醒协议。
- 建议持久记录来源与前后版本、时间、变更摘要、选择和分步结果；完整内容快照只在恢复确实需要时保存，不将凭据写入记录。保留期限、快照大小及清理策略待确定。

| 更新对象 | 实际执行职责 | 必须保留的区别 |
| --- | --- | --- |
| 扩展 | 复用现有代码安装 / 检查 / 回退；资源采用另行审阅 | 代码、贡献资源、运行数据和授权不同；存在本地代码修改时继续保护，不默认覆盖 |
| 角色卡 | 在原 Card 身份下核对包内容、资源引用及本地编辑，再显式采用 | 不以新建导入、重映射全部 ID 或清空重导入伪装成更新；不改写故事历史与已有 State |

## 作者作品与扩展依赖下载（待收束）

- 明确作品包内携带内容、外部资源引用和必需／可选安装依赖的区别；引用地址不自动成为下载或执行授权。
- 下载前展示主包与依赖清单：来源、版本要求、已安装状态、需新增或升级项、缺失与不兼容项。复用现有扩展依赖检查与确认安装路径，不重复开发安装器。
- “同步下载”当前按主包与配套依赖一起准备理解；是否并行下载、按需获取、支持暂停重试，以及是否包含持续跟随作者更新，均需进一步确定，不默认建设双向同步。
- 明确重复依赖去重、版本不兼容、循环或来源不可用时的处理；主包更新不能静默升级其他作品正在使用的共享依赖。
- 展示整体与逐项下载进度、失败原因、重试入口及结果。下载完成、安装完成、资源采用、授权与启用分别表达；不因文件已下载就宣布作品可用。
- 依赖部分失败时，是否保留已下载项、阻止采用主包或允许有限使用，按必需／可选合同决定。跨包下载与安装不假定全局原子事务。
- 自动检测覆盖有明确更新协议的作品来源与扩展来源；无版本协议的普通链接和本地 ZIP 不显示虚假的自动检测能力。

## 角色卡与贡献资源的冲突审阅（建议，待确认）

判断作者与用户各自改动，需要三个输入：**上次采用的作者原版 B、当前本地内容 L、候选作者新版 R**。仅比较 L 与 R 能展示差异，不能可靠判断改动归属。数据库修订号、Git commit 与真实作者内容基线不能互相冒充。

首先核对稳定资源身份、引用和包成员范围，再按资源 / 字段比较；文件重命名不应被当作新资源。Lore 文本、Script 源码、挂载配置、媒体字节、扩展代码及用户运行数据不能全部当作可合并文本。

| 情况 | 建议首版行为 |
| --- | --- |
| L 与 B 相同，仅作者更新 | 标为可采用作者新版，仍列入确认清单 |
| R 与 B 相同，仅本地更新 | 保留本地修改 |
| 两侧最终内容相同 | 无内容冲突，核对来源版本记录 |
| 两侧均修改且不同 | 标为需审阅；选择保留本地、采用作者版或手工编辑结果，不首发文本自动合并 |
| 作者删除、用户修改 / 仍被引用 | 展示删除与引用影响，未经解决不删除；本地删除与作者修改同样需审阅 |
| 没有可靠 B、来源身份不匹配 | 明确基线缺失或身份不匹配，不推断无冲突；允许查看两侧并另存副本，原位替换须另定显式合同 |

建议先按稳定资源 / 字段选择，不将成熟的逐行三方自动合并作为首版前置。脚本内容能合并不代表语义兼容；新权限仍需授权，保存、采用和开始执行保持各自合同。独立 Script 的同 ID 重导入仍按[现行 Script 计划](./loom-script-distribution-and-runtime-plan.md)创建副本，不因本计划全局改为自动更新。

最终确认前重新检查本地版本，防止预览后用户编辑被覆盖；内容、引用及采用记录的提交复用领域事务和版本保护，不另建资源数据库。跨文件、数据库与运行时不能假设一个事务：必须给出分步结果和恢复入口。

成功采用后保留“作者原版”和“带用户修改的结果”两种内容身份；部分采用、保留旧项或另存副本如何推进基线仍待决定，不能把合并结果直接当成下次作者基线，也不能未处理冲突就把整个包标记已更新。

## 已确认的讨论顺序与待决议题

2026-11-01 用户确认按以下三个阶段讨论。此顺序替代此前先收束完整身份、基线和冲突语义的建议；讨论顺序不等于实现授权，也不预设施工切片。

### 第一阶段：下载链路

先回答资源从哪里来、由谁下载、怎样完成下载：

- 首批来源与获取方式：Git、HTTPS 文件链接、本地包，以及作者作品与扩展的依赖来源。
- 浏览器与服务端各自承担哪些下载；下载产物放在哪里，如何交给后续导入。
- 主包与依赖怎样配套下载、复用已有产物、展示进度，以及失败、取消、重试和部分完成如何处理。
- 此阶段只明确获取所必需的来源和产物信息，不以前置完成三方合并、资源身份迁移或导入 UI 为条件。

### 第二阶段：更新检测、版本与通知链路

在来源与下载方式明确后，讨论怎样识别变化并告诉用户：

- 检查入口与时机、自动检测频率、失败与“已是最新”的区别。
- 作者版本号、Git branch / tag / commit 和内容摘要各自代表什么；如何区分新版、相同版本内容变化与固定版本。
- 哪些来源支持检测；检测结果怎样关联当前持有或已采用版本，以及如何进入新版下载。
- 通知位置、变更说明、去重、稍后处理、忽略版本与跨重启记录。
- 检测到新版、下载新版与采用新版分别表达，不因通知或检查而替换用户内容。

### 第三阶段：导入、已导入资源的更新与冲突保护

最后讨论资源进入应用及再次采用时的内容与权限语义：

- 首次导入、新版更新、另存副本的入口与区别。
- 作者原版、本地内容与候选新版的比较基线；Diff 展示、冲突提醒、保留本地、采用作者内容和用户存副本。
- 稳定资源身份、成员归属、引用与删除影响、部分采用及采用后的基线推进。
- 权限变化审阅与审计、授权及启用边界；失败恢复、版本保护和操作记录。

上文三方比较等方案继续作为第三阶段候选，不提前视为已批准合同。下载地址与包结构的既有安全校验仍属于获取边界；将权限审阅放在第三阶段不撤销这些校验。

下一轮从第一阶段的来源、下载执行位置和主包／依赖获取流程开始，不要求先完成后两阶段设计。

## 后续实施的验收依据

- 已修改的 Lore / Script 不被静默覆盖；稳定身份、引用、用户授权与运行数据得到保留，新增 / 删除 / 修改及用户选择可查。
- 预览后出现本地编辑、来源内容变化或并发采用时，原预览不能错误覆盖新状态；失败不能被记录为完成，重新进入能辨认实际状态。
- 成功及失败收据、待处理更新能按所确认的重启策略恢复；同一候选不重复轰炸提醒，检查失败不冒充最新。
- 作品及扩展依赖的新增、已安装复用、版本冲突和部分下载失败有明确结果；主包与依赖的进度、重试、采用及授权状态不混淆。
- 实现时选择覆盖真实变更的最小验证；公网下载、真实依赖安装、用户修改保留与 UI 人工验收分别记录，不以本地测试替代。

## 2026-11-03 合并范围与边界

原 Card 外部来源短后续不再独立维护。本页同时承接外部资源链接、用户指定来源、Git／非 Git 版本替换、包身份与来源版本、本地编辑保留、替换范围、缺失资源及失败恢复。不得通过清空重导入规避冲突，不因保存来源就自动下载、安装或授权。

来源可信度由用户决定，宿主负责授权范围内获取与校验；角色私有扩展的内嵌分发与外部引用并存，外部引用不自动物化。作者文件与 Timeline 不可变材料继续分属不同权威。关闭条件是选定来源类型后，用户可审阅版本与范围，并在本地修改、缺失和获取失败时得到明确结果。公网、跨平台和用户数据验收单独记录。此合并不新增自动更新或自动合并的实施授权。
