# Loom Script 单文件分发与运行计划

> **状态**：本轮 MD 单规则、捕获修剪、持久排序、流式投影与原生实验室已实现；渲染 CTX 连续更新、自动递归嵌套另立范围
> **更新**：2026-10-31
> **目标**：将 Script 从轻量 Renderer 格式扩展为通用单文件代码分发形式，复用扩展的运行环境和宿主能力。
> **本轮授权**：用户于 2026-10-22 明确要求开始实现。2026-10-23 进一步授权原生浏览器 Worker；实现与验证见第 12 节。其余通用执行器不纳入此次 Worker 实现。
> **当前讨论边界**：2026-10-31 仅回写并收束正则计划，不实施新格式或迁移。最新源码方向见第 21、23 节；渲染消费及嵌套渲染单列于第 22 节。第 23 节明确区分已确认原则、建议默认值与待决定事项。
> **后续授权**：用户已确认转入实施；上述“仅回写”描述此前讨论阶段。实施范围与顺序以第 24 节为准，不把第 22 节的全部渲染设想同时纳入本轮。

## 1. 已确认的产品定位

- Script 是比 Extension Package 更轻便的代码分发形式，Metadata 写在文件头部，不需要独立 Manifest。便于角色卡携带、单独分享及未来网络平台托管。
- 单文件是最终分发形式，不限制作者使用 TypeScript、多文件源码或构建工具开发。
- 渲染只是脚本的一项能力，不能继续用 Renderer 定义整个 Script。
- 作者和 AI 均可编写、修改和启动脚本。AI 调用不意味着只能按次执行；AI 启动的程序也可以持续运行。
- 扩展包本身可以携带独立脚本，不要求把该脚本改写成扩展模块。
- State 事件、动态 Prompt、Lore 激活等钩子属于整个扩展能力面，扩展和脚本均应能够使用；不为 Script 建立另一套独立业务 API。

### 创作价值与管理入口（2026-10-20 讨论，2026-10-22 回写）

- 产品层面 Script 也是扩展的一种形式；Extension Package 与 Script 区分的是分发和开发方式，不人为限制脚本只能使用较少能力。
- 核心价值是敏捷开发、便携单文件和独立采用。用户可在角色内新建、粘贴、编辑和添加脚本，无须进入扩展工程源码；扩展包仍从外部文件工程开发、打包、安装，不设置等价的 UI 加号创建包流程。
- 脚本总管理归扩展面板，不新增“资源总览 → 脚本”管理中心。角色上下文中的创建与添加入口仍需承接同一脚本身份，不因多个入口复制源码。
- 支持角色主作者提供 UI、接口和素材，子作者以可导入脚本扩充其功能；脚本允许引用角色或角色扩展的资源。依赖某扩展不要求修改该扩展原包。
- 扩展包也可携带独立脚本作为内部可选功能。脚本的独立性指创建、采用、编辑、刷新及分发，不要求独立进程或完全自包含依赖。
- 列表中的包内展开方式、筛选器、来源显示、编辑器布局及包默认开关与角色选择的优先规则仍为设计建议，尚未完成 UI 定稿。

## 2. 当前实现事实与入口

以下是 2026-10-22 实施后的入口；具体交付与验证范围见第 11 节。

- [现有 Script 合同](../../architecture/extensions/loom-script-runtime.md)及 [Metadata codec](../../../packages/application-runtime/src/scripts/loom-script-codec.ts)：接受 `client-sandbox`、`client`、`client-worker`、`server`；后三种无需 Renderer contribution，采用 `activate(ctx)` 入口。
- [Script Runtime](../../../packages/application-runtime/src/runtime/loom-scripts-runtime.ts)：源码以 Blob 保存，Document 保存 Metadata、源码引用、摘要和版本，Mount 保存采用关系与授权。当前不是可直接编辑的宿主源码目录，也不是把源码全文直接存进脚本文档。
- [Blob Store](../../../packages/asset-store/src/blobs/store.ts)：字节文件与 SQL 元数据协作；这一现状不决定后续工作区存储选择。
- [CodeAct 合同](../../architecture/application/agent/tool-system.md)：已有按次 QuickJS 执行及脚本附件读取；附件读取不等于正式文件执行入口，也不代表持久代码实例已经实现。
- [Extension SDK](../../../packages/extension-sdk/src/index.ts)及 [Host](../../../packages/extension-sdk/extension-host/src/instance.ts)：已有 State 订阅与实例注销。
- [Prompt Processor](../../../packages/extension-sdk/src/prompt-processing.ts)：已有按构建处理采用条目的正文及本轮激活结果的接口。它不是已经接好的任意脚本动态 Prompt 入口。

## 3. 执行环境与权限

### 已确认

脚本与扩展一样声明运行环境。用户不接受将首版主动收窄为仅 iframe，或预先排除其他环境。设计应覆盖 iframe、Worker、受控 JavaScript 沙箱、受信任 Client / Server 同进程执行及独立进程等讨论中的环境，并核对可复用执行器和缺口；不能仅增加声明字段就声称对应环境已支持。

分发形式、执行环境、能力授权和生命周期分别表达。沙箱化程度不由“作者写的还是 AI 写的”决定。未来允许 AI 启动持久执行实例，不把 CodeAct 当前按次释放的实现冻结成所有脚本的限制。

### 实施约束与待收束项

- 运行环境声明是请求，不自行授予权限；沿用宿主授权边界。
- 脚本本体同进程执行、只把渲染内容放进 iframe，不等于整个脚本受到 iframe 隔离。
- 不支持或未获授权的运行目标应明确不可用，不静默切换到权限更大的环境。
- 各环境的具体名称、入口形状、跨边界调用、终止能力与首版交付缺口，须在实施设计中逐项列出；如实际需要缩减已要求的范围，应向用户说明并决定。

## 4. 文件模型与 Timeline 工作区

### 已确认

脚本可以作为文件内容来源，但不锁定为真实磁盘文件。SQL 正文、Blob 或包内真实文件均可能成为底层实现，运行时按身份及版本取出代码即可。不得将用户此前偏好文件理解为已批准迁移到物理目录。

脚本接入 [Timeline 工作空间与 VFS 组织计划](./timeline-workspace-and-vfs-organization-plan.md)。该计划决定工作树身份、内容存储、并发与历史恢复；脚本系统不另建一套目录权威或独立回滚系统。随包文件与游玩生成文件可以采用不同存储。

2026-10-22 依赖核对：[Timeline 基础实施记录](../../archive/plans/timeline-foundation-implementation-plan.md) 已记录工作区文本随不可变树快照保存在共享 SQLite、二进制使用 Blob，正文 / State / Workspace 引用共同恢复。脚本应接入这一基础，不重开工作区物理存储选型；这不意味着作者脚本与包文件必须迁移进同一存储。该记录仍明确未新增脚本文件执行入口。本轮定向核对了 Workspace Store 与 Runtime 源码；未重新运行工作区恢复专项。

### 导入、原位编辑与导出（2026-10-22 确认）

- 再次导入脚本创建独立的新副本，不依据 Metadata ID、名称或版本自动覆盖已有脚本，也不增加自动更新检测。
- ID 和名称相同不意味着自动更新或合并；由用户或作者自行标记新区别。宿主仍需区分本地副本身份，不能让同名副本共用授权、运行实例或误指向旧资源；具体标记交互留给实施设计。
- 在 UI 中编辑包内脚本，就是直接修改当前所属包内的该脚本，不默认另存为个人或角色副本。角色或其他携带它的包后续导出时，应包含已保存的修改，而非重新取未修改的原始分发字节。
- 此决定替代此前“UI 修改包内脚本默认创建副本”的建议。其实现需核对包文件与可编辑内容的权威来源、导出路径，但不要求用户额外进行外部工程构建才能保存这类脚本编辑。

### 建议，尚非已冻结合同

- 普通辅助代码文件不必立即成为带完整 Metadata 的正式 Script；需要平台发现、管理、分发和启动时再采用正式脚本协议。
- 文件定义、挂载关系和运行实例分别管理。稳定 ID 不依赖显示名称、文件名或下载地址。
- AI 在 Timeline 工作区生成的文件与作者资源保持各自归属；是否有权修改作者脚本沿用实际编辑权限，不能把包内脚本一律改为只读或强制复制。

## 5. 保存与刷新

### 已确认

- 保存不等于启动，对用户和 AI 均如此；保存代码也不自动重启正在运行的脚本。执行仍通过明确启动或已采用的生命周期入口。
- 提供独立刷新按钮重新加载脚本，不要求整个页面刷新，也不要求切换角色。
- 刷新必须处理旧实例的停止与新实例的加载，不能简单再执行一次文件而保留旧监听器、定时器和闭包。

### 实施建议

实例绑定启动时采用的内容版本，界面可区分已保存版本和运行版本。准备及校验新代码后，停止并清理对应旧实例，再启动新版；启动失败明确展示。宿主托管资源可以清理，不能承诺任意同进程代码的副作用都可撤销。

刷新作用于选中采用范围还是该文件的全部实例、下一次按次调用采用哪个保存版本、失败后能否恢复旧实例及恢复范围，尚需实施合同明确。刷新不应无差别停止其他角色或全局实例。

## 6. 来源、采用范围与后台生命周期

### 已确认

| 情形 | 行为 |
| --- | --- |
| 全局脚本，包括全局扩展携带的独立脚本 | 可以全局运行，不因角色或 Timeline 切换而默认停止 |
| 当前角色携带并启用的脚本 | 随角色切换而卸载、加载；同角色切换 Timeline 不以此重启脚本 |
| Timeline 工作区内启动的脚本 | 切换离开该故事时停止并卸载其运行实例，不在后台继续运行；工作区文件仍按原有持久化与恢复合同保留，不因切换故事删除 |
| 显式停用脚本或其运行范围 | 停止对应实例 |
| 服务重启 | 按已保存的启用配置重新启动；不恢复旧内存，不默认补放停机期间的事件 |

包负责携带代码；来源归属与实际采用范围需要分别表达，不能把“来自全局扩展”硬编码成只允许全局实例。

### 实施建议与未决边界

- 同角色切换 Timeline 时保留角色实例，但更新上下文、重绑相关订阅；已发出的异步操作不能因为当前界面切换而写入新的 Timeline。
- Context 撤销、在途操作目标绑定与过期提交拒绝，应复用现有执行和恢复边界。
- Timeline 工作区脚本切离停止的决定不改变角色脚本的生命周期；重新进入故事后的启动遵循其已保存的采用配置和明确启动入口，不把文件存在视为启动授权。
- 剧情回滚不一律重启全局或角色实例。工作区代码、启用配置和内部持久状态如何恢复，以及哪些实例必须失效或重建，交由统一 Timeline 恢复合同收束；不得恢复文件后仍让过期实例无约束提交。
- 多窗口实例唯一性和协调暂缓讨论，不作为当前计划收束的阻塞项，也不提前建设去重或跨窗口协调系统。用户指出更常见的是多窗口分别打开不同角色；不据此宣称同角色多窗口行为已有保证。

## 7. 外部依赖与更新

### 已确认

允许外部 assets、CDN / 图床图片和代码依赖；不要求全部内嵌，不采用首版一律禁止远程依赖的建议。单文件描述分发入口，不保证所有依赖都在文件内。

不做脚本自动更新检测；再次导入按第 4 节创建新副本，已有脚本可直接编辑。外部依赖加载和缓存不等于自动更新脚本本体。

### 待收束

- 外部代码依赖的声明、解析基准、顺序、缓存、内容版本或摘要，以及加载失败时是否能启动。
- 资源随包导出与保留外链的规则，离线缺失的说明。
- 网络能力与依赖下载责任；各运行环境不能借加载依赖绕过其权限合同。
- 外部依赖远程内容变化、缓存失效与新权限请求的处理仍需设计；不借此引入脚本本体的自动更新、同 ID 覆盖或版本比较流程。

## 8. 共用能力面的衔接

已确认的实际需求包括作者根据好感度激活世界书、根据世界天数触发事件，以及 AI 保存可复用代码并启动后台世界演进。不能把这些需求归为仅 AI 使用或仅渲染使用。

讨论中的建议是区分两种语义：PromptBuild 根据本次 State 快照计算本轮内容；State 变化钩子处理需要发生并持久记录的事件。两者可以组合，但钩子、Prompt Contribution、消息投递和 Agent 触发的公共合同属于共用扩展能力面，不在本计划内另创一套。

相关 [Agent 通用触发计划](./agent-trigger-and-standing-resource-bindings-plan.md) 与 [CodeAct / VFS 计划](./codeact-vfs-tooling-plan.md) 负责各自入口。脚本持续运行不自动授予消息发送或 Agent 调用能力。

## 9. 单文件协议的设计参考

以下是从用户脚本生态讨论得到的建议，不是已全部批准的字段或机制：

- 静态解析 Metadata，建立索引和导入时不执行源码；明确格式版本、重复字段和未知执行声明的处理。
- 身份独立于名称；Metadata ID 和作者字段不证明来源可信。重导入创建新副本已按第 4 节确认，不再保留按同 ID 自动更新的候选。
- 权限请求与隔离环境分开，避免“无权限声明反而获得直接宿主访问”的歧义。
- 作者发布版本与实际内容摘要分开，避免 AI 每次保存都必须发布新版本。
- 显式运行入口及宿主追踪的清理机制，避免停用、刷新后残留重复订阅。

参考：[Tampermonkey 权限语义](https://www.tampermonkey.net/documentation.php?locale=en&q=grant)、[外部依赖与完整性](https://www.tampermonkey.net/documentation.php?locale=en&q=externals)、[Violentmonkey Metadata](https://violentmonkey.github.io/api/metadata-block/)。参考用于设计比较，不要求兼容其协议。

## 11. 2026-10-22 实施记录

### 已接通

- 扩展面板新增“脚本”页，复用主从工作台：新建、导入、原位保存、导出、按全局/当前角色采用、逐项授权、启停及刷新选中实例。角色编辑入口复用同一文档身份。新建仅产生草稿，保存不创建或启动 Mount。
- Metadata 静态解析支持无 Renderer 的 Client / Server 脚本、自动申请对应 `runtime.client` / `runtime.server` 信任及有序 `@require`。不支持的环境拒绝导入，未获授权的代码不执行。
- 同 ID/同名重复导入分配新的本地文档身份。目录 Apply 根据捕获时的附件位置映射文档身份，不依据 Metadata ID 认领原件。
- 包内脚本 UI 保存仍写原文档；包 ZIP、角色导出和目录快照用已保存字节覆盖 Manifest 指定的原始路径。重命名 UI 文件名不改变包中的引用路径。
- Card 采用跨 Owner 脚本时，沿用 Attachment 导出独立快照，导入分配新的 Card-owned 副本、禁用且无授权；不改变导出前原脚本归属。同 Card 同时携带其扩展包时，包内脚本和采用快照分别保留，导入不按 Metadata ID 自动合并。若要求继续绑定包内贡献，需要后续显式引用型附件协议。
- Mount 保存 `adoptedDocumentVersion`。保存源码不更新采用版本；显式刷新检查新版执行环境授权后更新版本，以 Mount 版本触发局部清理和启动。启动时补齐已有启用 Mount 的采用版本。删除源码不会借历史版本继续执行。
- Client / Server 脚本各复用现有 Extension Host 的实例、信号、注册句柄及清理；只使用内存模块记录，不伪造已安装扩展文档。相同脚本的多个 Mount 独立管理。
- 全局实例保留；角色切换移除角色实例，同角色切换 Timeline 保留实例。Client 上下文读取当前 Timeline，已经发出的读操作保持原目标并再次校验；显式订阅绑定的目标不会自动改写成另一故事。
- `resolveLoomScriptRendererMounts` 为只读解析；实际工作台通过 `reconcileLoomScriptRuntime` 同步运行范围。查看 Inspector 不切换后台脚本范围。
- `@require` 按声明顺序下载经典 JavaScript 并与入口拼接；只在真实运行边界内执行。卸载/刷新取消未完成下载，迟到结果不启动。失败报告诊断。Client 遵循浏览器 CORS；Server 每项限制 4 MiB、15 秒超时。不实现远端 ESM 递归依赖解析或脚本自动更新。
- 服务启动按保存的全局采用配置启动 Server 脚本；关闭服务清理实例。角色实例由工作台当前角色上下文接入，不复原旧 JavaScript 内存或补放事件。

### 当前执行矩阵

| 声明 / 路径 | 真实执行方式 | 当前入口与限制 |
| --- | --- | --- |

## 16. 2026-10-25 贡献、运行入口与文本处理能力（静态已实现，动态接口待后续）

### 运行入口与贡献相互独立

脚本不限于渲染。静默后台代码可以仅提供 `activate(ctx)`，不声明任何贡献；执行环境及所需能力仍须声明和授权。允许只有声明、只有代码、声明加代码三种组合。不为后台运行新增强制的“后台贡献”，也不把全部运行时 API 塞入 Metadata。

当前 Metadata 静态贡献仅支持 Renderer 是协议缺口，不代表已有 Client / Worker / Server 后台入口只能渲染。本轮协议设计同时纳入正则规则与文本提取器的静态贡献。

### 三种使用方式

| 方式 | 作者行为 | 平台责任与生命周期 |
| --- | --- | --- |
| 静态贡献 | 文件声明规则或提取器 | 无须执行 JS 即可发现、校验；按采用范围和已采用版本解析，由平台流水线执行，停用撤销 |
| 动态注册 | 运行代码通过宿主 API 注册 | 规则/提取器定义复用静态合同；注册归运行实例，返回清理句柄，停用、刷新或崩溃时宿主回收 |
| 按次调用 | 代码传入文本或正式历史处理请求，获取结果 | 不自动加入持续流水线，不产生持久注册；复用既有处理能力、结果与权限边界 |

三者是已认可的设计方向，不代表 API 已实现。先落实静态贡献；动态注册按共用 Extension SDK 能力设计，扩展和脚本共同使用。具体方法名、可用运行环境、范围与授权需先形成接口合同。

### 执行与副作用边界

- 普通字符串处理优先使用 JavaScript 原生 RegExp、replace、matchAll；只有需要平台结果结构、诊断、执行预算或正式历史上下文时，才增加宿主调用，不重复包装所有语言内建能力。
- 替换规则产出文本变换；提取器产出结构化结果/Artifact。两者可以共享匹配实现，但保留各自输出语义，不强行合成同一种贡献。
- 静态与动态注册复用定义、校验和底层执行逻辑。动态规则不能形成第二套匹配/替换行为。
- 提取到数据不自动写 State、激活世界书、发送消息或调用 AI；这些是需要单独明确操作与授权的副作用，避免显示刷新导致重复剧情操作。
- 有效规则须按处理请求的 Timeline / Session / 消费预设等上下文解析，不能只读取当前浏览器页面激活的角色。浏览器动态注册不能默认对 Server 后台处理可用；需稳定参与后台 Prompt 的规则优先采用静态声明。
- 不承诺迁移或统一消除正则执行本身的性能风险；继续沿用并核对宿主已有预算和错误行为，不把 Worker 可终止能力误认为主线程正则也已获得同样保护。

### 改造顺序与成本约束

1. 扩充文件与 Metadata 协议，支持无 JS 的规则/提取器贡献，确定多行正文表达及稳定贡献 ID。
2. 接入按请求上下文解析的采用版本，转换为现有文本流水线输入；复用匹配、替换、提取、阶段、深度和检查记录。
3. 以完整脚本为唯一编辑入口，提供只读规则摘要、定位和样本文本测试；首版不实现表单反写源码，不重排或重建作者的 JS。
4. 设计旧规则身份到 Script/Contribution 的迁移，保留预设采用、单条禁用、排序覆盖、Renderer match 引用；处理同一脚本多范围采用时的身份与重复执行规则。存量默认一条旧规则对应一个脚本是当前实施建议，不视为已执行迁移。
5. 统一角色/预设/扩展包及 ST 导入导出，旧格式可在导入边界转换，最终退出旧规则的独立写入路径，避免长期双份权威与同步层。

- **State**：Mount 分开保存用户 overrides 和 adoptedSettings；配置保存不变化运行修订，启用/刷新时冻结有效配置与源码版本。角色配置继承全局已采用值，缺失值回到作者默认值。全局、工作区、预设、角色按此顺序覆盖，同文档只选一个 Mount，选择先于 enabled 检查。移除范围恢复继承；不删除脚本。单文件导出只带作者定义；角色/预设附件的用户配置作为包内采用数据携带，导入仍不带执行授权。
- **Migration**：旧规则逐条以 Blob+Script+Mount+旧记录删除的原子事务转换。通过内部贡献地址映射保留旧引用；不依据 Metadata ID 合并。旧导入格式在边界转换为 Script，不维持独立可写规则文档；旧规则页收束为摘要/检查与完整源码入口。存量 Extractor 不做强制迁移，新静态 Extractor 可用。

- **Acceptance and validation**：纯声明不执行 JS；相同脚本不重复处理且角色 OFF 有效；配置保存不改源码、不重启，刷新生效；旧规则引用和两轮包导出导入保持；完整源码/标签/配置往返；针对这些行为运行定向测试和跨模块类型检查，不以类型检查代替浏览器视觉验收。
- **Boundary**：动态注册与按次 SDK 文本能力保持第 16 节方向，首版交付静态贡献；不借此新增受控沙箱。依赖 JS 的声明须由宿主确认对应运行修订已激活；浏览器代码不能被后台流水线当成常驻服务，无法满足依赖时明确诊断，不偷偷执行代码。

- **匹配/提取结果到 Renderer 的绑定是独立消费合同。** 如需把捕获数据直接交给组件或侧栏，由提取/投影与 Renderer 绑定解决，不要求先拼出 HTML/Markdown，也不把组件挂载作为替换规则的第二种 effect。既有 Renderer 引用须在衔接时保持兼容，不借本次讨论静默删除。
- 保留 ST 的原始字符串替换与 HTML 文档渲染兼容行为，不自动把旧规则转换成组件。作者仍可使用 HTML；组件化是新的创作路径，不是所有简单替换的前置条件。
- 典型目标为手机消息框、状态栏、骰子结果、可展开卡片等轻量消息视图。复杂、长期存活的界面继续使用工作台、独立页面等既有 Surface，不把消息正则入口扩展成通用大型 UI 容器。
- 单文件分发不限制作者使用 `.html`、`.tsx`、多文件工程和构建工具开发。原生源码与构建产物的分发属于渲染资源/脚本/扩展合同；Markdown 正则只需保留作者要替换的原文，不承担 TSX 编译或组件分发协议。

### 作者语言、渲染环境与输入协议

- `html`、`tsx`、未来的 `vue` 标识作者源码的语言和对应工具链，不是新的正则类型，也不决定隔离方式。首轮组件方向以 React TSX 为目标；Vue 作为后续编译及框架适配方向，不视为本轮必须同时实现。TSX 具体 JSX runtime 需有明确构建约定，不能仅凭扩展名猜测。
- 普通 DOM（`direct`）、Shadow DOM（`shadow`）、iframe（`sandbox-iframe`）沿用现有挂载适配器。HTML、React、Vue 均不天然等同于某一种环境。Shadow DOM 提供样式/DOM 封装，不提供作者代码权限隔离。
- 组件源码先编译成渲染模块；匹配发生时只传数据，不把捕获内容填入 TSX/Vue 源码再编译或执行。消息正文中的 `tsx`/`vue` 围栏不是执行授权，源码语言标记只用于已采用的作者资源。
- 匹配描述和组件实现分离，使平台不执行作者组件模块也能读取匹配规则、权限和入口。构建产物应携带静态描述与可加载代码；组件加载发生在获授权的实际运行环境内。
- 编号捕获可映射成 `$1` 等 props，命名捕获推荐映射成语义字段；在 `<p>{$1}</p>` 中，`$1` 是组件接收的变量，不是 React 内建的正则替换指令。最终映射字段、缺失捕获表示、配置与上下文的命名空间需在实现合同中确定。
- 捕获默认是字符串或缺失值。需要数字、对象等输入时须显式转换及运行时校验；TypeScript 类型注解不自动解析或校验模型输出。普通文本 props 按文本渲染，原始 HTML 注入须明确区分，不自动把捕获文本当代码执行。
- 所有框架适配共享匹配数据、用户配置和宿主上下文的输入含义。iframe 通过受控通道传递可序列化数据，在 frame 内更新组件；不跨环境传递 React element、函数或 DOM 引用，也不通过反复重载 iframe 模拟 props 更新。

### 文本消费与直接数据入口

```text
文本替换规则 → 文本产物 → 消息内容识别 → HTML 等既有显示路径
匹配/提取结果 → 独立绑定 ───┐
                          ├→ 共同 Renderer 合同 → Surface/Scope/挂载环境
JS 脚本或扩展 → 业务数据 ──┘
```

- 匹配/提取路径提供锚点与数据，独立绑定负责输入映射；JS 脚本可直接提供业务数据并注册 Renderer，无须伪造一条替换规则或生成 HTML 字符串。没有消息匹配的脚本可以面向已有 tail、工作台等 Surface；有消息目标时仍须满足消息锚点与 Scope 合同，不能任意注入宿主 DOM。
- React/Vue 辅助层对接现有 `mount(root, context)`、实例 `update(context)` 与 disposer；不新增与 Renderer Host 并行的注册、排序、授权或清理系统。框架渲染实现与 `direct/shadow/sandbox-iframe` 挂载适配器是不同职责。
- 通过 `narrative.entry.inline`、`agent.message.inline` 等既有入口接入，保留锚点重叠诊断、Surface 仲裁、采用作用域和撤销行为。具体需要修改哪些 Surface 接线应先逐条核对，不仅根据 surface 名称存在就宣称能力已完成。
- 新显示结构保留原始消息；组件输出不写回历史正文，不默认进入 Prompt 阶段。文本转换链与显示锚点的坐标关系、多个匹配与重叠规则的处理在实施合同中明确，避免改变已有规则顺序。
- 稳定挂载期间，平台提交新的有效输入时应更新原组件，避免流式增量导致反复重建和丢失局部状态；匹配位置移动时不能仅以字符偏移作为实例身份。保存配置/源码不自动采纳或重启的既有约定保持，props 更新机制不隐式改变配置生效时机。匹配消失、停用、刷新或 Scope 切换时卸载并清理事件和任务。
- 不承诺离屏卸载、页面刷新后仍保留组件局部状态。当前消息虚拟化允许卸载并重建轻量视图；需要长期保留的数据由明确的数据存储负责，不能把 React 局部 state 当作业务持久化。

### 持续交互通过渲染上下文接收更新（2026-10-31 收束）

- 手机聊天、Galgame 等持续交互界面可以通过渲染宿主提供的 CTX 接收当前作用域的输入及更新，不必靠正则反复把 `$1` 拼入 HTML/JS。正则替换仍适合文字处理和简单模板；动态界面不要求先注册一条正则。
- 正则捕获/提取结果可以作为渲染输入的一种来源，但不是唯一来源，也不等于已运行 IIFE 会自动接收到新值。数据交付与实例更新由宿主合同明确；作者负责格式解释、气泡增长、加载动画及完成状态，不要求平台内置 Message、UpdateVariable 或 game 协议。
- 当前 [SDK](../../../packages/extension-sdk/src/index.ts) 已有 `ClientNodeDisplayProjectionContext` 的 rawText/displayText、`ClientRendererContext`、`mount/update` 和 `loom:renderer-context` frame 消息。它们是可复用基础，不代表普通 HTML iframe 已自动拥有 CTX，也不代表稳定的流式输入更新已经接通。实现时须明确输入来自原文、显示投影还是提取结果，不能将不同输入混成一个无来源的字符串。
- 流式 CTX 后续合同至少明确：所属消息/视图身份、当前输入快照、生成中/完成/中断状态、更新交付与卸载清理。具体字段和推送方式在渲染实施时确定，不在计划中虚构已存在的订阅 API。iframe 通过受控桥接接收可序列化输入，不因此获得宿主对象或全局消息访问权。
- 连续挂载期间，应更新同一实例而非每次重跑页面源码；是否需要保留气泡等局部状态由作者实现。现有 `HtmlPreview` 在 value 变化时重建 frame，不能作为稳定流式 CTX 更新已验收的证据，也不承诺任意旧 HTML 自动获得增量更新能力。
- “整条回复完成后展示、单条记录闭合后展示、记录内部逐字展示”是作者实现的效果层级，不设为三种脚本类型或强制平台模式。第三种效果不是正则首版的前置条件；通用渲染上下文更新属于本节，正则只需支持第 23 节的快照处理。

### 自动识别与嵌套渲染（单独记录，不阻塞正则收束）

- 文本消费方向保留闭合的 `html` Markdown 围栏，并沿用完整 HTML 文档的兼容识别；不将任意 `<div>` 或任意代码示例都当成可执行页面。围栏只是内容标识，不授予宿主代码权限。Markdown 规则的替换正文直接包含这段围栏，不再套一层分发围栏。
- `<Closeup>` 内出现 `<Image>` 是真实创作场景。若 Image 规则先生成带围栏的 HTML，再被 Closeup 模板放进另一个 HTML 文档，宿主的 Markdown 识别不会自动在 iframe 内再运行；结果可能显示裸代码或破坏文档。规则顺序与捕获清理可以避免不需要的嵌套，但不能代替渲染组合能力。
- 允许有意的嵌套渲染方向：仅展示图片时，外层模板可直接使用 `<img>`；确需独立交互视图时，由渲染合同明确组合子视图或子 iframe。浏览器能嵌套 iframe，不等于平台已有递归消息渲染能力。用户观察到的 ST 偶发嵌套成功尚未定位原因，不作为兼容保证。
- 不默认递归扫描所有 iframe 正文，不自动执行其中的新围栏。未来子视图须继承明确的权限边界、输入通道和父子生命周期；父视图卸载时清理子视图，避免递归循环和无界展开。具体子视图协议与嵌套限制在渲染实施时定稿，不增加到正则 KV。
- 流式时的实例身份、输入更新与撤销归渲染宿主；正则提交当前快照的变换结果，不承诺其已成为最终结果。作者可以用未闭合内容驱动加载动画或持续更新；不再要求所有原始输入片段完整后才允许显示。作者数据的完整性与 HTML 文档识别、代码权限分别处理，不能互相代替。

## 23. 2026-10-31 Markdown 正则、捕获清理、流式与顺序（讨论收束，待实施）

本节回写最近几轮讨论，覆盖第 21、22 节中较早的格式与职责表述；不是已发布协议或实施完成记录。用户本轮只授权更新计划。以下已确认原则与建议默认值分开，末尾列出仍需用户决定的行为。

### 已确认的最小职责

- 正则规则属于文本处理管线：选择输入范围、匹配/捕获、清理捕获内容、替换；替换正文为空就是删除匹配部分。替换正文可以是普通文本、Markdown 或包含 HTML/CSS/JS 的文档，规则不解释其用途。
- 保留来源/角色、作用阶段、深度、启用、顺序等现有能力；不因强调最小职责而删除既有分类、推理提升或提取能力，它们仍遵守各自合同。修改正文、显示投影和 Prompt 投影不能混为同一次持久化写入。
- 渲染识别、隔离方式、TSX 编译、Surface、Artifact/侧栏及嵌套视图均属于第 22 节。正则对渲染的服务是保留原文、可控处理顺序和持续提交流式快照结果，不负责判断任意作者格式的记录完整性或选择运行环境。
- 声明式规则与运行代码共享管理能力，不强求拥有相同进程、排序或源码语法。静态规则不启动作者进程；动态注册使用相同规则定义与处理管线，运行实例负责注册的生命周期。

### Markdown 携带方式

已确认使用 Markdown，避免独立 `.loom` 语言、JSON 字符串中的大型源码和 JS 注释容器。建议单条规则采用 **YAML 前置信息 + 后续全文作为替换正文**；不需要额外的 `regex` 代码围栏。下例展示字段与原文关系，不表示解析器已支持这些字段：

````markdown
---
id: example.phone
name: 手机消息框
tags: [UI]
regex: '<phone>([\s\S]*?)</phone>'
regex_flags: g
phases: [display]
order: 10
---
```html
<div class="phone">$1</div>
```
````

- `regex` 是表达式源码，`regex_flags` 单独承载 flags；单引号 YAML 字符串保留反斜杠，内部单引号按 YAML 规则写成两个单引号，多行表达式可使用字面量块。不是另造一套正则转义规则，也不要求手工加 JS 的 `/…/flags` 外壳。
- 只解析文件开头的前置信息。其结束分隔行后的内容就是替换正文，不先运行 Markdown 渲染，不去掉代码围栏，不自动包 `html`，不进行 HTML 转义。建议分隔行自身的行终止符不属于正文，此后的空行、空格、换行风格与结尾换行均保留；仅有空白的正文不是空替换。
- **多规则文件退出本轮范围。** 用户明确它只是尚未验证且没有当前需求的设想；本轮新 MD 一份文件携带一条规则，不讨论分段格式、整组拆分或文件内排序。此前把多规则样例列为实施前置条件的要求撤回；既有 `.loom.js` 静态贡献保持兼容，不据此删减已有能力。
- 作者可在前置信息声明可配置变量，由平台托管用户取值；用户改配置不必编辑 Metadata。继续全文编辑、摘要与样本测试，不恢复双向表单。旧 `.loom.js` 静态贡献继续支持，转换需显式进行且不改变已采用版本。

### 工作台保存、排序与统一 CRUD（2026-10-31 再次修订）

- `.md` 是源码及单文件携带格式，不要求工作台每个操作都回写真实磁盘文件。继续由脚本文档引用源码 Blob；修改正文或前置信息时保存源码版本，导出时得到完整 MD。切换为 Markdown 所需的媒体类型适配仍待实施。
- 本轮一份 MD 就是一条原子规则。Metadata 的 `order` 可以提供同组规则的初始默认次序，不是脱离所有范围的绝对执行位置；工作台排序不要求手工编辑该字段。
- **最终确认：拖动即持久保存，刷新后保留。** 用户撤回临时排序方案，不再区分临时拖动与另行保存。复用当前集合/采用范围的排序记录，不需要重写 MD 源码；已保存排列优先于 Metadata 初始值，不将两个顺序值简单相加。源码默认值后续改变也不静默覆盖用户已经保存的排列。
- 在角色、预设或已有扩展包内编排的顺序，作为该范围的内容配置保存并随对应包导出；个人全局顺序归个人配置，跨组的有效管线调整归相应运行上下文。只修改实际选定范围，不因调整一处顺序连带重写所有采用位置。单独导出 MD 仍保留源码，不把所属集合的所有排序信息塞进单文件。
- 组间默认执行顺序为：**当前采用的预设 → 角色 → 独立扩展（存在时）→ 用户个人全局规则**。个人全局指用户自己创建且不属于某个扩展的资源。组间可以拖动调整实际执行顺序；来源目录、Tag 和搜索排序本身不隐式改变管线。该顺序不改变同一脚本的角色采用优先级及明确 OFF 覆盖全局的合同。
- 当前 [Mount 更新](../../../packages/application-runtime/src/runtime/loom-scripts-runtime.ts) 会持久保存独立采用文档的 `orderIndex`；[角色导出](../../../packages/application-runtime/src/cards/workspace.ts) 也会携带该值，可作为本轮接线基础。其他范围的拖拽与导出需实际接通，不能仅根据已有字段宣称完成。现有规则级 order、旧规则迁移与 `TextPipelineOverride.orderedRuleIds` 不在本次文档修订中删除或迁移。
- 不按“作者”和“用户”建立两套 CRUD。操作面向用户实际选择的资源与所属范围：可以在角色、预设、已有扩展包内新建、编辑、删除规则或脚本，也可以创建个人全局项；身份不决定能否编辑自己持有的资源。
- 工作台提供新建入口与模板，自动创建对应的脚本文档和源码，不要求用户先去文件系统创建 `.rules.md` 或 `.loom.js` 再导入。对已有扩展包内新增轻量脚本，不等同于新增 UI 创建完整扩展工程的功能。
- 在角色/预设/扩展包内直接新增或修改资源，改变该本地包的内容并保存，后续导出应体现这些改动；不自动改成一个全局副本或隐藏覆盖。规则源码的修改与用户配置、启停、移除采用及排序各自保存到对应记录；删除资源也不能静默等同于仅取消采用。
- 以上是目标行为，不代表每个所有权范围的 UI、包写入和导出已接通。实现时须沿真实资源身份完成 CRUD、版本保存与包往返，保持“保存不自动启动/重启”和代码授权独立；保存排序也不能采用未保存源码或触发代码重启。

### 捕获内容清理（建议字段 `capture_remove`）

保留这项能力。它解决 `<think>` 中提及标签被后续规则误匹配，以及 `<Closeup>` 内含 `<Image>` 时不希望生成嵌套渲染标记等实际需求；不将其误解成首尾空白修剪。

```yaml
capture_remove:
  - '<Image>'
  - '</Image>'
```

- **建议固定语义**：匹配完成后，对将要插入替换正文的捕获值按列表顺序进行区分大小写的字面量全量删除，再展开替换引用。同一捕获被引用多次，使用相同清理结果。编号捕获、命名捕获及完整匹配引用保持一致的清理语义。
- 上例仅移除两个标签，保留其间 URL/文字；`['<', '>']` 仅移除尖括号。要删掉整个 Image 块及其内容，应由另一条匹配替换规则完成。这里不增加“清理表达式里再嵌套正则”的第二套管线。
- 不修改正则正在匹配的源文本，不清理未命中的文字，也不清理模板作者新写的 HTML 标签。输出交给下一条规则后，下一条才会看到清理效果。例如先匹配完整 think 块，清理其中捕获正文的尖括号，再由模板补回外层 think 标签。
- 当前 ST 的 `trimStrings` 确实在捕获替换时逐项进行字面量删除，并包含 ST 自身的宏展开。兼容导入须区分可等价映射的字面量与待支持的宏，不能把宏名称当普通删除串后假称兼容。原生格式不为此新造一套隐式宏语言。
- 原生替换引用继续依赖现有文本合同；ST 的 `$0` / `{{match}}` 须在导入边界正确映射完整匹配，不能原样落成字面量。`$$`、编号与命名捕获、缺失捕获及清理时机要有明确样本，不通过 JS `eval` 实现兼容。

### 处理阶段、持久化与推理分块

- 保留“只改变显示”和“只改变提示词”的需求，以处理阶段正向表达，不通过两个“仅……”复选框的未勾选状态隐式开启持久化。现有 `display / prompt / classify` 分别承接显示投影、提示词投影和保存前处理的方向；具体输入/提交路径仍需逐项核对。
- 显示与提示词投影不改写保存的消息，各自从保存的内容计算，不串成“显示结果再送给 Prompt”的管线。用户可选择一者或两者；关闭后重新计算对应投影，不需要撤销消息写入。
- 保存前处理会改变正式正文或结构，须明确选择。停用规则只影响后续处理，不自动还原已保存消息或重新处理全部历史。建议同一规则的保存前处理与显示/提示词投影互斥，以免同一替换重复执行；需要不同逻辑时分别声明规则，不引入组合含义不清的 `persist: true`。
- 将正文中的推理移入推理块是明确的结构动作，沿用 `promote-reasoning`，由匹配、目标捕获和推理块属性描述；不能只靠持久化布尔值表达。提交时保证移除正文片段与创建推理块一致完成。推理块的显示方式与后续回传模型的策略分别沿用 visibility/replay，建议默认折叠且不回传。
- 流式阶段可做临时分区和显示，不对每个快照重复执行结构持久化；正常结束、取消和中断分别沿正式提交路径处理。保存前处理不自动重跑历史数据，原文证据与恢复能力沿现有消息/版本合同核对，不另建一套隐式迁移。

### 流式快照处理（2026-10-31 收束，取代三档平台模式）

- **匹配成功不等于输入完整。** `$` 在当前临时末尾也能匹配；非贪婪表达式也可能从 think 中提及的 `<Status>` 匹配到正文的 `</Status>`。不自动补闭合标签，不把所谓“智能强匹配”作为默认纠错。
- 推理与正文的分区应在流式消费之前就开始，而非只在最终持久化时处理。Provider 独立 reasoning 通道保持独立；项目明确支持的文本 think 标记，在开始标记成立后即分区，尚未收齐的标记尾部暂存判定。任意作者标签不能由平台猜成推理边界。
- 平台提供“显示规则组是否参加流式快照处理”这一能力；建议默认关闭，由作者明确开启，用户可以关闭。关闭只影响生成中的规则预览，消息完成后仍正常处理，不关闭普通文字的流式显示。不将效果层级拆成三种平台模式，也不提供强行升级任意模板为增量界面的开关。
- 每次从当前原始输入快照重新执行适用规则链，保留顺序，不把上次变换结果当下一次输入；可按显示节奏合并更新，最终快照必须交付。正则计算本身不写回消息或触发业务操作；这一选项不改变 Prompt 阶段、持久化触发语义或渲染代码权限。
- 作者可以匹配完整记录，也可以显式匹配未闭合尾部，使用结果显示空壳、加载动画或增长中的文本。平台不负责理解所有记录格式，不要求原始捕获内容完整才允许提交显示结果；此前统一等待完整片段的建议被本条取代。HTML 文档识别和渲染执行仍遵守各自合同，不等于任意半截页面源码都可以执行。
- 预览结果允许修正或撤回，不承诺只增不减。清理与依赖它的替换规则应使用一致的组级预览策略；不自动提前运行未允许预览的规则。检查器说明当前快照、跳过项和执行顺序，不能让最终态测试冒充流式覆盖。
- 用户提供的 `/<UpdateVariable(?:variable)?>(?!.*<\/UpdateVariable(?:variable)?>)\s*(.*)\s*$/gsi` 表达式用于“更新中”状态：开始标签完整时可匹配空捕获，内容增长时 `$1` 增长，完整结束标签到达后不再匹配，由另一条完成规则接管。半截结束标签仍可能进入 `$1`，由作者的表达式或界面处理。负向前瞻与当前快照已足以支持此类行为，不因此新增平台记录解析器。
- `$1` 被替换进源码不等于同一 iframe/IIFE 收到了数据更新。持续交互优先通过第 22 节的渲染 CTX 合同接收输入；简单正则模板保持可用，不强制为加载动画引入 JS 或 Renderer。
- 中断或失败不是正常完成。保留原始内容及已知推理分区，向消费者暴露未完成状态；不把未闭合 think 内容悄悄改成正文，不丢弃原文。分区接线属于明确支持的推理协议，不借此推导任意作者格式，也不能宣称现有 classify 已覆盖所有 delta。

### 规则顺序与启停

- 同一有效脚本只执行一次，先确定角色/全局采用优先级，再判断是否启用；角色明确关闭覆盖全局启用。规则顺序不能绕过关闭或授权。
- 同一管线中，后续规则读取前面规则的输出。这既支持“清理/规范化 → 替换”，也意味着可能再次命中已生成文本；不能为了防止重复渲染而全局禁止后续规则匹配替换结果。需要的嵌套清理由作者写出，渲染组合另行处理。
- 尚未调整时，按预设、角色、独立扩展、个人全局的组序组合，组内采用资源 Metadata 的默认顺序，相同顺序以稳定身份兜底。用户拖拽后采用已持久保存的对应范围排列，不反写 MD 源码。不得使用异步注册完成先后决定文本结果，不再为本轮设计 MD 文件内的多规则顺序。
- 静态贡献和动态注册进入同一有效规则序列；动态规则的所属实例/脚本和稳定规则 ID 必须明确。停用、刷新或实例结束撤销其贡献，不在每次注册时另开一条顺序不明的管线。动态 SDK 合同仍待实施。
- 来源目录、Tag、折叠和搜索只是管理视图，不改变执行顺序。排序拖拽写入明确范围并跨刷新保留；检查器显示最终执行顺序及其配置来源，不将搜索结果排列冒充执行配置。
- 运行代码本身不因列表排序而获得启动依赖或持续进程优先级；只有它贡献的有序规则参与文本顺序。其他脚本的列表顺序可以只是显示顺序，不能承诺所有脚本按此执行。

### 当前源码事实与实施缺口（2026-10-31 只读核对）

- [文本流水线](../../../packages/application-runtime/src/transforms/history-text.ts) 已有阶段、匹配与替换逻辑，但没有本节的 Markdown 解析、捕获清理及显示流式快照处理的完整接线。完整匹配替换已有 `$&`，不能假定它将 `$0` 等价处理。
- [ST 导入](../../../extensions/st-data-compat/src/normalizer/regex.ts) 当前对 `trimStrings` 报告无法等价映射；完整匹配宏与 `$0` 的映射也需与实际替换器对齐。ST 的编辑触发和宏行为应在导入边界解释，不能机械复制字段后当作已支持。
- [显示投影](../../../apps/studio-client/src/features/message-content/model/use-display-projection.ts) 当前会在 streaming 路径直接返回原文；最终分类或已有 classify 阶段不等于已实现本节的流式分区。需沿真实输入路径逐步接入，避免新旧路径同时处理。
- [消息分段](../../../apps/studio-client/src/features/message-content/model/message-segments.ts) 已有 HTML 围栏/文档识别，[HTML 预览](../../../apps/studio-client/src/features/message-content/ui/html-preview.tsx) 使用隔离 frame。现有文档闭合判断与 frame 创建能力不证明支持嵌套消费或流式实例稳定更新；这些留在第 22 节验收。

### 收束状态与范围撤回

R1 的职责方向已经收束为作者可启用的流式快照处理，不再要求“完整片段才可交给执行型渲染”，也不增加三档平台模式。默认关闭与用户可关闭作为本轮建议值记录；持续界面的 CTX 更新归第 22 节，不能成为要求正则承担记录协议的理由。

原 R2 围绕“同一文件内多条规则是否拆散、交错”的问题随多规则文件退出本轮。拖拽持久化已确认：直接保存当前范围排列，刷新保留，并由相应包/上下文携带，不要求反写源码。工作台 CRUD 按实际所属资源保存，不按作者/用户身份拆分，也不要求手工创建文件才可在包内新建。此处不再保留排序持久化的待澄清项。

`capture_remove` 等 KV 命名、YAML 编码、换行保真、稳定身份排序与错误定位由实现合同确定，不逐项要求用户审批。多规则容器、分段语法及其排序没有本轮需求或授权，不再作为协议定稿前置项。职责收束仍不等于协议已经实现。

### 实施范围与可观察验收

后续以“格式适配 → 文本流水线 → 导入/编辑/诊断”接通最小流程；复用既有运行与采用合同，不同时建设新脚本语言、资源 Tag 全平台或嵌套 Renderer。重点验收：

1. 单规则 MD 的完整复制、导入导出保留正则反斜杠、真实换行、`*/`、HTML/CSS/JS 和 Markdown 围栏；空正文确实删除，空白正文保留空白。正文中的分隔线和标题不被误拆成规则。
2. think 内提及 Status、Closeup 内出现 Image：捕获清理只改指定捕获值，后续规则收到预期文本；移除标签与移除整块两种效果可区分，不假称已经支持嵌套渲染。
3. 对同一消息按多个位置切分流式输入，覆盖半截起始标签、尚未闭合区间、临时末尾、正常结束及中断；每个快照重算不叠加变换，已分区的推理不泄漏到正文显示规则。使用上述 UpdateVariable 表达式验证空捕获、内容增长、半截结束标签及完成后退出，允许作者有意匹配未闭合内容。最终文本结果与相同规则链的完整输入计算一致。
4. 初始组序与 Metadata 默认值稳定；拖动后保存，刷新仍保留，对应角色/预设/扩展包导出再导入保留编排，其他采用范围不被改写。排序不改源码或代码运行 revision，不采用未保存源码；已有用户排列不被 Metadata 默认值静默覆盖。相同顺序值、不同注册完成时序、静态/动态混用时结果确定，角色 OFF、停用清理及保存不重启保持原合同。未接通动态路径时明确报告。
5. ST 的字面量 trim、完整/编号/命名/缺失捕获、宏及阶段行为逐项核对；不支持的导入项明确诊断，不静默改写含义。渲染的识别、权限与实例行为另按第 22 节验收。
6. 显示/提示词投影不回写消息、不彼此串联；保存前替换与推理分块在正式提交时生效，停用不自动重写历史。推理片段从正文移除与创建 reasoning 记录一致完成，流式预览不重复持久化。
7. 用户可从工作台在角色、预设、已有扩展包内创建规则或脚本，保存后重新打开仍存在，导出/导入对应包保留本地改动；不要求预建磁盘文件，不默默改成全局资源。编辑、删除、取消采用和启停各自目标明确，保存不自动运行代码。

## 25. 实施与验收记录（2026-10-31）

本轮已接通以下流程：

- `.md` 单规则：YAML frontmatter + 原文替换正文，统一解析到现有 Script Contribution；创建、更新、测试、导入导出使用正确 MIME，旧 JS 源码继续可读，已有数据不强制重写。新建规则和新迁移的旧规则生成 MD。编辑器使用 YAML/Markdown 混合高亮。
- `capture_remove` 在捕获引用展开时执行；ST 字面量 trim 与完整匹配引用转入原生语义，未支持的 trim 宏保留诊断。`regex_flags` 无 g 时只处理首匹配，有 g 时处理全部。
- 显示流式：默认关闭，显式开启后按原始快照重算；Agent 回复及 Timeline 执行区的流式正文都接入。客户端有约 100ms 采样节流，最终快照不等待节流；不把显示投影写回消息。
- 分组与排序：具体所有者分组；默认预设→角色→扩展→个人，拖动保存 Mount 顺序/组序，不重写源码或刷新代码实例。其他采用范围不被重排。尚未建立角色采用的全局继承条目不允许直接做角色排序，避免生成隐式 OFF 覆盖。
- 包内 CRUD：角色、预设、已安装扩展可从管理面板创建/导入/编辑/删除 Script；角色和预设附件携带顺序/组序。扩展导出收集本安装新增 Script、保存源码和排序，并移除明确删除的贡献声明；不把重新导入当成代码授权。

### 原生 Dev Preview 实验室

入口 `/dev/preview/regex`，主界面左侧可编辑原文本、右侧替换文本/正式消息渲染，规则源码和规则顺序在下方展开。支持播放、暂停、单字符步进、切片滑块、立即结束、真实提交和 SQLite 重读。

12 个用例包括捕获修剪边界、命名/编号/完整/缺失捕获与美元转义、规则级联及顺序交换、Unicode 零宽首匹配/全局匹配、UpdateVariable 临时末尾/半截结束标签、三档手机消息流式、持久化推理提升与三阶段隔离、嵌套冲突、修剪避免嵌套、作者显式 iframe 嵌套。标准输入有可核对预期，自定义输入不套用样例断言。

后端由 Vite 的仅开发同源入口启动独立 SQLite / Blob / ApplicationRuntime，位置 `.artifacts/regex-preview`。不接生产或用户数据目录。规则保存/启用用原生 API，流式使用原生 projectHistory，结束快照复用原生文本处理器和采用解析。持久化通过真实 invokeAgentTurn：只有 Provider 输出由本地样例提供；正式 classify、推理分块、Transcript 保存及显示/提示词投影均未 Mock。刷新和 SQLite 关闭重开均保留记录。

### 明确边界

### 旧规则 Script 的 MD 迁移与统一管理（2026-11-01，已实施）

- 自动迁移接入 ApplicationRuntime.initialize，在扩展启动前运行。仅处理带旧文本资源引用映射、单条声明式规则且无执行代码/设置/依赖的旧 JS 格式 Script；不改写原始历史版本。
- 每个 Script 的最新版本与 Mount 已采用/固定版本在同一 SQLite 事务内分别转换为 `.rule.md`，保留 Script/规则 ID、来源归属、标签、版本声明、配置、启停、排序和 runtimeRevision。Mount 指向等价新版本，不把未刷新的最新内容偷偷启用。已有 MD 版本直接保留，重复启动不再迁移。不可无损转换项原样保留，并输出带 Script ID 的启动诊断。
