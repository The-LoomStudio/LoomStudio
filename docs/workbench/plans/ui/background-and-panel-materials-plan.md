> **日期**：2026-09-13

## 目标

提供第一方背景控制与配套面板材质，使静态图片和扩展动态背景都能通过前景正确呈现。背景选择、透明度、模糊、可读性、保存与恢复形成一个闭环；不能以“背景已经挂载”替代完成交付。

## 外部实现调研：Odysseia Forum

Odysseia 将背景和玻璃材质拆成三个层次：`WallpaperBackdrop` 负责背景图与暗化，`ThemeProvider` 根据背景可见度计算一组表面 Token，`surfaces.css` 再把这些 Token 应用到 `od-chrome-layer`、`od-chrome-surface`、`od-content-surface`、`od-floating-glass` 等有限语义层。它没有让每个组件自行计算透明度，也没有把文字颜色透明化。

它的运行时算法按背景可见度派生多组透明度，而不是全局设置一个 opacity：Chrome、内容、浮层、输入和边框使用不同强度；边框保持更高不透明度，文本保持实色。玻璃模式还区分 `on`、`off`、`auto`，`auto` 只在 `CSS.supports('backdrop-filter: blur(1px)')` 时启用。`backdrop-filter` 不支持时，仍有可读的半透明／实色表面。

该项目的样式指南明确要求：内容可见性与文字颜色不能依赖玻璃效果；弹窗通常使用实色层；固定定位面板避免被带有 `backdrop-filter` 的祖先包裹。移动端 TopBar 为此单独创建玻璃背景层，避免 Header 成为 fixed 面板的定位边界。这个经验比简单增加 `z-index` 更值得保留。

Odysseia 还使用 `color-mix()` 生成语义表面，并把 `glassBlur` 限制在 `0–32px`。这证明“透明度、模糊、边框和层级分开控制”可以落地，但其具体百分比、Token 名称和组件数量不能直接搬进 Loom；Loom 应保留自己的 `--loom-*` 语义体系。

## 浏览器与性能边界

`backdrop-filter` 只会处理元素后方的合成内容；目标后方必须确实有可见纹理或图像，过实的底色会让效果看起来像普通半透明。祖先的 `opacity`、`filter`、mask、clip-path、混合模式及部分 `will-change` 可能改变背景采样边界。`z-index` 只解决绘制顺序，不能保证采样正确。

因此样板必须同时检查：目标元素和祖先的计算样式、几何尺寸、背景底色、滚动容器、Portal 挂载位置，以及动画期间的采样结果。`CSS.supports()` 只能确认属性可解析，不能证明实际采样到了背景。高模糊、超大区域和大量重叠玻璃面板应在真实浏览器中测量后决定上限，不在 Plan 中承诺固定帧率。

## 对 Loom 的落地建议

1. 采用“Stage 背景 → 有限宿主材质层 → 内容”的结构。材质层使用独立背板，内容负责滚动与交互；不对整个 Stage 或正文列表设置整体 opacity。
2. 首版只定义少量稳定层级：`background`、`chrome`、`content`、`raised`、`floating`、`solid`。每层拥有独立 fill alpha、blur、border 和降级值；不要给每个业务组件建立玻璃 Token。
3. 背景可见度只影响表面派生值，不影响文本、焦点环、状态色和交互命中。实色模式必须是完整可用的降级路径。
4. 弹窗、菜单和 Portal 默认使用实色或独立浮层背板；不让它们继承任意祖先的滤镜。需要玻璃时，直接挂到 Host 约定的浮层层级。
5. 先用静态纹理背景验证采样，再接动态 Renderer。动态背景不能通过增加更多 blur 弥补纹理不足。

这些建议来自本地 Odysseia 源码调研和浏览器规范经验；它们是本 Plan 的实施方向，不表示已经改变 Loom 的 CSS 或组件合同。

## 决策

1. 背景与面板材质共同设计、实施和验收。毛玻璃是正式范围，不是后续增强项。
2. Renderer 负责背景内容，宿主负责材质、可读性和用户控制。复用 `shell.background`，不新增平行背景宿主。
3. 底色 alpha 与模糊强度分别控制；不以整个容器的 opacity 控制材质，避免文字与按钮一起变淡。
4. 不把全部 surface 颜色 Token 改成透明，不给每层嵌套控件或每条消息机械增加滤镜。保留实色选择，Custom CSS 内容不被官方设置重写。
5. 扩展页面、声明式设置与组件使用能力归 [Extension DX Plan](../extension-developer-experience.md#3-扩展页面声明式设置与组件使用)，不作为本计划前置。
6. 背景注册供 AI 阅读的必需信息为路径、名称、描述；身份、归属和解析信息供程序使用。支持跨 Package 引用，跨包身份消歧与资源访问仍走宿主合同。
7. 资源消失或来源扩展卸载时移除有效注册，背景不再出现在面板或 AI 候选中，不做自动找回。旧持久化引用可以失效，不为此改写历史 State。
8. 角色卡通过其携带的扩展声明携带背景引用；这是目标导出行为，不代表当前已实现。引用跨包资源不等于自动打包所有外部依赖文件。
9. 材质区域由实施者根据真实布局评估，不适合透明的区域使用实色。可读性由用户选择材质开关，不建设自动对比度修正；性能上限在实现后根据测量确定。

## 实现约束

布局容器、材质背板和内容分别承担布局、采样和交互职责，不要求一律增加三层 DOM。遵守 [CSS 与主题合同](../../../architecture/ui/css-and-theming.md)，不通过大块关键伪元素、任意全局 CSS 注入或极大 z-index 修补。

材质背板与滚动内容分离；一块面板优先一个背板。滤镜、祖先 opacity、mask、clip-path、混合模式和相关 will-change 可能改变背景采样边界；stacking context 不等于 Backdrop Root，不能把问题统一归因于 z-index 或 transform。开关动画、Portal 和嵌套表面必须结合目标浏览器核对。

材质 Token 只表达底色、模糊、边界及实色模式等稳定角色，命名在实现设计时冻结。参数只作用于明确选定区域，不靠无边界继承传播到所有输入框与弹窗。`@supports` 只能说明属性支持，不能证明采样正确。

### 背景管理的信息架构

背景管理应放在官方设置的 `外观` 分类中，并拆成“背景”和“材质”两个子页。背景页回答“后面显示什么”，材质页回答“前景如何呈现”。它不需要 ST 那种根级常驻导航：Loom 已经有设置和扩展工作台，且未来可以由 AI 根据世界状态自动切换。设置页仍要提供人工检查和覆盖入口，否则用户无法解释当前背景来自哪里，也无法关闭自动行为。

毛玻璃选项属于“材质”而不是“背景”：它控制前景表面的合成方式，不能被理解为一种背景资源。但它必须与背景联动，因为没有可见图片或动态纹理时通常缺少明显效果。没有背景时仍显示并保存毛玻璃设置，不静默清除；可以给出“需要可见背景才能产生明显效果”的说明或跳转背景页入口。关闭背景不应重置材质偏好，重新启用背景后恢复原设置。

建议的信息结构：

```text
设置
└── 外观
    ├── 背景
    │   ├── 当前背景
    │   ├── 横图预览
    │   ├── 来源与自动切换
    │   └── 材质状态摘要：实色 / 半透明 / 毛玻璃
    └── 材质
        ├── 表面模式：实色 / 半透明 / 毛玻璃
        ├── 模糊强度
        ├── 表面透明度
        ├── 边框强度
        └── 可读性与降级
```

背景页不复制完整材质控制，只显示状态摘要并跳转到材质页。未来 AI 自动切换背景时，材质偏好默认保持不变；场景联动材质必须是单独、明确的用户选项。

背景库应采用横向资源卡或横向预览列表，显示预览图、名称、来源和当前状态。AI 切换使用统一开关，不给每张图片增加授权设置。已确认失效的资源移出候选，暂时加载失败只显示失败状态。比例裁切只影响预览，不改变实际背景资源的定位语义。

资源不需要物理集中：角色背景可以留在角色文件夹，扩展背景可以留在各自 Package 的 `assets`，官方背景由宿主管理。统一的是**受控资源身份、来源和读取 API**，不是文件位置。扩展用 Manifest / JSON 提供静态元数据，再用正式 API 注册可用背景；宿主负责权限、来源展示、卸载清理和失效诊断。

AI 从当前有效注册中读取路径、名称和描述，再更新背景选择。路径需要能解析到对应来源，不能通过重名相对路径猜测 Package。此前提出的四级优先级并未冻结，本轮改为统一开关与 State 消费提案，不继续扩展多级抢占规则。

### State、上下文与开关：待确认提案

建议场景背景选择使用现有 Timeline State，复用 Branch / Revision，不新增独立 KV。背景是原生能力，其最小 State 模板应由官方背景能力定义，不依赖延期的 The World；The World 后续复用该合同。具体 State 路径、模板接入旧 Timeline 的方式仍需设计。

背景不应作为脱离世界结构的顶层孤立键，而应建模为 State 中可组装的 Component。组件定义由官方背景能力提供，The World 的初始化 Contribution 可以把它挂载到自己的世界或场景实体中；作者卡也可以在创建 Timeline 时显式组装同一组件。这样既保持背景能力的通用性，又让它与地点、场景等世界数据处在相近的 State / EC 结构位置。

需要区分两个层次：地点或场景实体上的背景候选／引用，表示“这里可使用哪些背景”；当前 Timeline / Branch 的活动背景引用，表示“此刻实际显示哪一个”。前者可以随地点或场景变化，后者是宿主读取和渲染的当前选择。两者都使用受控资源身份，不直接保存物理路径。没有地点或场景绑定时，官方仍可提供全局默认组件值，但不应把它设计成另一套 KV 世界模型。

背景候选的路径／名称／描述通过运行上下文提供给 AI，Context 是本次调用的输入，不是另一份持久化权威。State 只存选中的背景引用；候选注册和用户外观偏好不复制进世界 State。

建议开关控制“是否跟随 State 中的场景背景”：开启时读取当前 Timeline / Branch 最新 State；关闭时显示已有的人工选择或无背景，保留场景 State，不清空、不反复回写。再次开启直接消费最新 State。缺少有效场景引用时使用人工选择或无背景，不保留上一世界画面。

关闭时不主动向 AI 提供背景候选与更新指引，可补充“不需填写背景”的说明以减少无效输出；但提示不是可靠约束，即使通用 State 工具或作者脚本仍修改该字段，界面也不能自动切换。本提案控制的是显示跟随，并不声称禁止一切来源写 State；如果产品需要禁止写入，应另行冻结实际写权限合同。

## 验证预算与停止条件

- 文档阶段仅检查本次 Diff、相对链接和归属一致性，不跑应用测试。
- 实施时用最小定向检查覆盖偏好恢复、显式替换及停用／异常恢复；公共类型变化才补对应 package 类型检查，不默认跑全仓套件。
- 客观浏览器诊断聚焦采样、层级、尺寸、命中、滚动与动画期间行为；包含带纹理静态背景和动态 Renderer。性能只在具体效果出现风险时测量。
- 人工验收覆盖模糊真实生效、文字对比度、开关动画、滚动、弹窗、移动布局和操作手感；自动检查不替代用户判断。
