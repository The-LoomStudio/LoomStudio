# 可选依赖与通用组件评估计划

> **状态**：Deferred / 候选保留，未选型、未试验、未接入正式产品。
> **日期**：2026-10-25
> **本轮授权**：整理独立 Plan；不安装依赖、不修改 FileTree、不替换 Agent 或数据库框架。

## 1. 目标与用户决定

通过小范围可撤销试验，判断外部库接管通用能力后，减少的自建维护是否足以抵偿引入、适配、迁移和后续升级成本。热门程度和功能清单不构成采用理由。

用户明确要求标准交互组件暂缓引入。FileTree 已有自己的逻辑与渲染，保留正式实现；替代方案放到下一步试验。Agent 框架同样暂不引入，包括对话中提到的“派 / Pi”类候选；具体项目和版本未确认，不将名称推测当作已选型。

与[架构精简主计划](../../archive/plans/architecture-code-reduction-plan.md)独立。主计划可基于现有依赖推进，不等待本计划，也不能借主计划静默安装这里的候选。

## 2. 候选与优先级

| 候选方向 | 可以接管的工作 | 必须证明的适配成本 | 当前状态 |
| --- | --- | --- | --- |
| 树交互库，例如 React Aria Tree | 通用选择、焦点、键盘、拖拽语义 | 项目节点与渲染、动态高度虚拟化、展开行、批处理部分失败、内联编辑、主题和动画能否保留；是否需要 fork 或额外平行状态 | 下一步可选试验，优先保留；不代表锁定该库 |
| `@trpc/tanstack-react-query` | typed query/mutation options、key/filter 配置 | 相比现有 tRPC + Query 实现能删除多少包装；连接身份、请求取消、错误与调用封装是否保持 | 可选；先看主计划 A1 的实际剩余成本 |
| React Hook Form 等表单库 | 字段绑定、dirty/error/reset、复杂表单状态 | 相比原生表单及现有组件的净收益；异步保存、外部更新、草稿和焦点兼容 | 候选，不扩张为全工作台配置引擎 |
| Drizzle 等类型化数据库工具 | 表结构、查询类型、部分映射 | `node:sqlite`、共享连接/事务、Commit Journal、CAS、修订/恢复和迁移如何保留 | 低优先级；不直接迁移真实数据库 |
| Pi 等 Agent 通用框架 | 待选定具体项目后核对执行与工具能力 | 能否覆盖或干净让出 Loom 的流式输出、审批、恢复、Swipe、事务和权限；适配是否反而更大 | 暂缓；不开展当前试验 |
| 通用服务端框架或整套 UI 框架 | 待明确真实缺口 | 新增生命周期、配置、样式与业务适配是否超过可删除量 | 暂缓；不为降行数更换技术栈 |
| Query Devtools 等开发工具 | 查询缓存与请求状态观察 | 与当前版本/运行环境兼容、开发限定和敏感数据展示边界 | 有实际调试需要时评估；不算代码精简收益 |

以上均是候选，不要求全部测试或全部引入。当前未发现必须替换已用 AI SDK、Radix、TanStack Virtual 的证据。

## 3. 后续试验方式

用户启动某个试验后，主 Agent 先冻结单一候选、目标行为、版本、写集与停止条件。一次选择一个代表性闭环，不先铺设抽象层，也不默认批量评估所有库。

1. **建立基线**：列出实际希望删除的实现和现有行为。比较对象必须包括“维持现状”与“仅用原生/现有依赖精简”，不能只比较两种新库。
2. **隔离试验**：在开发预览或独立实验工作区使用内存夹具，不接真实账户、真实 Provider 或生产数据；依赖只进入批准的试验写集，不改变正式入口。具体位置在启动时决定，不提前创建工程。
3. **完成适配**：复用真实渲染/领域接口验证边界，不能只展示库的默认 Demo；保留正式实现供行为对照。
4. **集中验证**：完成一个交互闭环后，检查已列出的行为、键盘/焦点、数据完整性和相关包体/加载影响；主观外观由用户验收。无需顺带建设新的测试框架。
5. **给出采用或保留结论**：报告净收益、限制、迁移与撤回成本。用户决定采用后，再形成具体迁移写集和删除旧实现的完成条件；试验成功不自动授权正式接入。

FileTree 首个试验的必查内容：单选/多选、展开与键盘导航、受控选择、合法/非法拖放、内联编辑、右键与批量操作、部分失败保留选择、长列表窗口化和动态行、现有自定义行渲染、焦点与动效偏好。沿用[当前树实现](../../../apps/studio-client/src/shared/ui/file-tree/file-tree.tsx)及其真实消费者，不以改产品行为来适配库。

## 4. 决策记录与停止条件

每个试验记录：

| 项目 | 要回答的问题 |
| --- | --- |
| 所有权 | 库接管了哪部分状态/行为，哪些仍由 Loom 拥有？ |
| 净维护量 | 能删哪些手写源码、测试专用适配和重复配置？新适配、配置、补丁和测试是多少？ |
| 契约 | 是否改变用户交互、权限、数据、错误和恢复语义？ |
| 运行成本 | 对包体、加载、内存或交互性能有何相关实测影响？与源码行数分别记录 |
| 引入与升级 | 许可证、版本/运行时兼容、上游维护、是否需要 fork；后续升级由谁维护哪些适配？ |
| 迁移与撤回 | 直接消费者改动范围、迁移投入、旧路径删除条件与撤回方式是什么？ |
| 结论 | 采用 / 保留现状 / 暂缓；证据与尚未验证项是什么？ |

出现以下情况停止扩展试验并报告：必须破坏既定合同才能接入；依赖私有 API 或长期 fork 才能满足核心需求；新旧可写状态需长期并存；完成最小适配后仍不能展示净收益。停止不等于证明库本身不好，只表示当前项目不值得迁移。

不预设减行比例，不把依赖代码移出仓库当作复杂度消失。无需为了交付试验而强行采用一个库。
